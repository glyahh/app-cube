## 1. 已确认目标

- 用户始终使用同一聊天框与同一套 Agent 能力；开发、测试是具体任务的职责状态，不是两套产品或强制手动切换的模式。
- 用户可继续开发，后台测试按启动时的独立快照完成，不混入后续修改。
- 测试任务可生成测试代码/规则/夹具，但不自动修业务代码。修复必须是用户授权后的独立开发步骤。
- 修复方案可手动或对话修改；批准修复默认包含相关已选测试的回归，新增范围和权限仍须批准。
- 旧报告仅是线索；先在最新版本复现再修复。方案有实质变化时重新确认。
- 回归失败后，在已批准范围内继续定位、最小修复、验证；无进展、扩大范围或新增权限时停止并报告。
- 最终未修好保留修改与失败现场，用户决定继续或回档，不自动全部撤销、不假称交付完成。
- 每次成功都须有实际错误、根因依据、修改内容与版本化验证结果；不默认发布生产。
- 代码及上下文回档、保留用户修改/严格恢复两种方式，沿用独立回档专项约束。

## 2. 当前源码与最小改造位置

Java `AgentRunRequestFactory` 负责归属和工作区，`AgentRunService` / `AppRunCoordinator` 按 app 串行开发，`AgentRunPersistence` 记录运行与消息；Python `core/runtime.py` 分类并选 Backend，`core/streaming_runtime.py` 以 thread 调用图，文件工具和 Shell 产生实际修改。前端 `AppChatView.vue` 复用原聊天和工作台。

当前任务类型与成功事件未体现本设计完整授权/验证闭环，固定 `app:{appId}` thread 也未提供回档分支资格。当前手动文件保存有文件内容版本及文件锁，但不等于和所有 Agent/Shell/后台写入共用工作区恢复闸门。上述为源码事实，未做运行复现。

建议扩展现有请求、权限与事件，不新增 Python HTTP 服务或第二套聊天助手：

- Java 增加 `DevelopmentTask`、`RepairPlanRevision`、`ExecutionApproval`、`VerificationLink` 和文件修改台账；委派现有 Worker 执行。
- Python 复用 DeepAgents 的观察、行动、再观察循环（ReAct），执行权限由任务授权与 Backend 限制，不靠 Prompt 自律。
- 回归作为独立测试子任务，关联开发任务与修复版本，不改成开发 Agent 的自评。
- 跨应用身份、任务版本和上下文 epoch 按共同契约核对；实施时才更新实际协议，不在本轮伪造已支持接口。

## 3. 从用户要求到实际执行

1. **识别意图**：测试、修改、解释或明确的组合请求；识别不等于授权。模糊请求或新增高风险副作用只确认真实分歧，不反复问基础原则。
2. **形成方案**：范围、当前版本、目标业务要求、预期变更、受影响文件/模块、实际错误、前置依赖、回归清单、权限与风险。
3. **版本化批准**：用户批准的是方案 revision、具体目标与权限，不是永久“任意修改”。方案被编辑后旧批准不能套到新内容。
4. **执行前检查**：取得当前开发写入资格，重新读最新源码/相关证据；旧报告需先最新复现。短暂冻结写入建立消息前快照和版本锚点，再执行。
5. **最小修改**：优先复用已有模块；每次修改记录来源、before/after 和 patch。不得重新生成整项目来绕过修复。
6. **回归验证**：绑定修复后的固定版本与原批准的相关测试，记录真实输入、输出、退出码和最终业务状态；用户后续修改不混进该轮。
7. **结算**：成功、未完成、无进展、阻塞、取消分别展示；根因推断未获证据时标推断。用户代码或环境又变化时旧成功不得代表当前状态。

只要求测试的任务不会因失败自动变成开发；组合请求也在内部拆任务，写入前遵循批准策略。明确自然语言批准可作为确认渠道，必须记录批准内容与 revision；模糊“看看”或“继续”不自动授予新的业务写入/安装权限。

## 4. 批准范围与无进展检测

建议授权包含：需求/问题标识、方案 hash、appId、baseVersion、contextEpoch、允许修改模块/路径和目的、允许命令/环境能力、相关回归 caseId/标准版本、副作用边界。路径清单不是唯一约束，不能在允许文件中植入无关功能。

执行中重新校验：权限未撤销、任务未取消、上下文未回档、工作区基准未被其他写入改变。版本漂移不机械套旧 patch；重新读取和复现，实质方案改变则重新确认。

无进展建议由实际信号判断：重复同一错误签名且输入/代码/环境未变、重复相同无效 patch、关键指标/断言无改善、所需依赖权限无法满足、无法取得可靠证据。该机制待固定失败样本校准；不是按花费金额停止，也不是模型一句“快修好”即可无限执行。

允许有新证据的范围内迭代，每次保留 failure/attempt。更改断言、跳过必要项、屏蔽异常、将失败改不适用不属于修复。基础设施重试先确认副作用可控，不能重复支付/通知类操作。

## 5. 任务状态与跨任务衔接

```text
REQUESTED -> PLANNING -> AWAITING_APPROVAL -> APPROVED
APPROVED -> BASELINE_CHECK -> REPRODUCING -> APPLYING -> VERIFYING
VERIFYING -> COMPLETED（修复及已批准回归有实际证据）
VERIFYING -> REPRODUCING（有进展、同授权范围内）
执行中 -> NEEDS_APPROVAL / BLOCKED / NO_PROGRESS / FAILED
执行中 -> CANCELLING -> CANCELLED 或 STOP_FAILED
回档请求 -> 原任务执行资格撤销，不再进入当前新分支
```

开发状态是业务闭环状态，不替代 Worker 的 `run.completed`。同一用户消息可以关联规划、修改、回归子任务，各有独立 runId 和事件资格；用户不必感知内部 thread 分拆。

纯开发功能任务的必要验证由方案声明，不自动把所有测试或 QPS 全选。无测试环境不能宣称已修好；可以显示“代码已修改，验证阻塞”，保留可检查补丁，不暗中发布。

## 6. 结果与交付结构建议

`DevelopmentTask`：appId、originMessageId、taskId、parentTaskId、branchId、contextEpoch、授权 revision、输入基准、执行状态。

`RepairPlanRevision`：问题/实际错误、根因依据及推断标记、修改目的/范围、候选 patch、验收标准、相关测试与环境权限。

`RepairAttempt`：本次 before/after hash、changeSetIds、动作与证据、重复/改善信号、失败签名、下一步依据。

`VerificationLink`：开发 taskId、测试轮次、修复后的内容版本、标准、caseId、真实结果与最终状态。

用户交付只展示简洁摘要，详细证据可展开：实际问题、原因依据、修改差异、执行验证、版本资格、未测/风险、复跑步骤。运行说明、部署/回退步骤按实际环境提供，不自动创建生产发布动作。

## 7. 与其他三项的边界

- 导入成功只是文件接入；没有安装确认不运行，缺环境不冒充基线已建立。新项目生成仍保留，导入永远不覆盖已有应用。
- 测试规则与报告归属独立；修复不能修改冻结标准使测试变绿，旧报告修复需最新复现。
- 代码修改让图谱过期，按用户同步偏好与应用开关更新；不能把旧推断当当前关系。图谱失败不改业务验收结论，定位依据不足如实说明。
- 回档优先停止所有相关资源并撤销旧资格；新上下文不再检索旧 repair plan、工具结果、失败摘要或备份。失败现场保留不意味着 AI 有永久读取权。

## 8. 后续实施顺序（尚未授权）

1. 先评审原聊天中方案/批准/回归/未完成的前端状态，不实现两套模式 UI。

3. 分别验证版本漂移、范围扩张、无进展、取消和来源台账，保留现有生成回归。
4. 对照流程矩阵与回档矩阵完成全面验收，再提供交付/回退证据。

无进展规则、协议能力、权限级别、环境适配与源文件变更采集均须实际验证。文档落盘不是实现完成，不启动或重启后端来“验证文档”。
