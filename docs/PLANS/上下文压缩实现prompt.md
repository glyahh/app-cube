# 上下文压缩机制 —— 实现设计 Prompt

> 用法：把下面 `---` 之内的内容整体交给 coding agent。
> 这份 prompt 已经过一轮对**本仓库源码**的核验，把原设计里几处与本系统实际不符的假设改掉了。改动点集中在「第 0 节 系统现状」和「第 4 节 必须先解决的前置问题」。

---

## 角色与目标

你是这个仓库的架构设计者。仓库是一个 Java 后端（Spring Boot + MySQL + Redis）的 AI 代码生成平台：SSE 流式管线把 LLM 输出收敛为可版本化的端侧制品（单页 HTML / 多文件 / Vue 工程）。

**要设计的东西**：一套上下文压缩机制，即「对话变长之后怎么让发给模型的上下文变小，又不丢任务连续性」。

**现状**：已有一套简陋的会话记忆（V4），但它有两个问题——摘要每轮都滚一次（固定税），且没有分层。目标是改造成分层机制。

**本文档只要求产出设计方案，不要求写实现代码。** 但方案必须落到本仓库的具体文件与函数上，不能停在抽象层。

## 0. 系统现状（已核验，以这些为准）

这几条是**核验过源码的**，跟"一般 agent 系统该有的样子"不一样，请以这里为准。括号里是文件位置。

### 0.1 消息类型里没有「工具结果」

`ChatHistoryMessageTypeEnum` 只有三个值：`USER / AI / ERROR`（`model/enums/ChatHistoryMessageTypeEnum.java:9-11`）。**没有 `TOOL`。**

工具结果由流式处理器直接塞进 LangChain4j 的内存（`dev/langchain4j/service/AiServiceStreamingResponseHandler.java:163-165`，`ToolExecutionResultMessage.from(...)` 之后直接 `addToMemory(...)`），**不落 `chat_history` 表**。

而 AI 轨重建时只回填 USER / AI 两种消息（`core/memory/ChatHistoryAiMemoryRebuildSupport.java:106-129`，clear 在 line 87）。

**这条的后果你要在方案里正面回答**：工具结果既不落库、重建时又会整段消失，那么"针对工具输出的压缩"到底作用在哪个集合上？如果它只活在 Redis 热窗口里（`conversation.memory.chat-ttl-seconds=600`，`config/ConversationMemoryProperties.java:78`，**10 分钟 TTL**），压缩该挂在什么时机？

### 0.2 摘要"算空"已经被洗成非空占位符，而且被当成成功落库

`parseSummaryResponse` 在摘要文本为空时**返回占位串** `（历史对话摘要）/（历史回复摘要）`，不抛异常、不返回空（`core/memory/ChatHistorySchemaMigrationSupport.java:712-718`）。

调用方拿到后**无条件写库**并 `mergedCount++`（`service/impl/ChatHistoryServiceImpl.java:894-898`），同时把源消息 id 记入 merged → **原文从此被排除出 AI 轨**。

**这条的后果**：一条零信息量的"摘要"进入真相源，源消息被标记已合并。任何"检查摘要非空"的兜底都会失效——因为它**看起来是非空的**。

### 0.3 摘要是在事务里做 LLM 调用，而且是 `while(true)` 循环

`trySummarizeOldestRoundsIfNeeded` 带 `@Transactional(rollbackFor = Exception.class)`（`ChatHistoryServiceImpl.java:813-814`），方法体内 `while(true)`（line 839），每次迭代都调一次 LLM（`summarizeTwoRoundsWithAi` / `summarizeWithExistingSummary`，line 864 / 877），然后写库（line 896）。

### 0.4 现有压缩是「每轮触发」，不是罕见事件

`trySummarizeOldestRoundsIfNeeded` 在 `ChatToGenCodeImpl.java:155` 和 `:232` **每次生成都会被调用**。触发条件是 `countUnmergedDbUserRounds > TARGET_UNMERGED_DB_USER_ROUNDS(=2)`（`ChatHistoryServiceImpl.java:830-831, 843-844`；常量在 `ChatHistoryConstant.java:16`）。

也就是说：**一旦超过 3 轮，每个轮边界都会滚一次摘要**，每轮至少 1 次 LLM 调用，且每次都要把"现有摘要 + 新轮"重发一遍。100 轮会话 ≈ 100 次额外摘要调用。

（`replaceConversationSummary` 不设大小上限，line 896。）

### 0.5 全仓没有「上下文窗口」这个配置

闸门用的是**轮数**（见 0.4），窗口用的是**条数**：`MessageWindowChatMemory.maxMessages = 160`（`ChatHistoryConstant.java:22`）。

`application.yml` 里的 `max-tokens` 是**输出上限**，不是窗口。

**这条很关键**：如果你想用"占用 / 窗口 ≥ 比例"做阈值，那么"窗口"这个数在当前系统里**没有来源**，得先把它落成配置（见第 4 节）。

顺带：token 用量数据其实**已经存在**——`AiModelMonitorListener.java:107-113` 从 `metadata().tokenUsage()` 取了 input/output/total，但只喂给了监控计数器，**没接到控制流**。

### 0.6 模型与端点

`ai.platform.base-url: https://dashscope.aliyuncs.com/compatible-mode/v1`（`application-local-a.yml:21`）。

模型（同文件 33-79）：摘要用 `qwen3.6-max-preview`，**输出上限 `max-tokens: 8192`**；生成用 `qwen3.6-plus`(12288) / `qwen3.6-flash`(32768)。

重试：模型 `max-retries: 2`（line 37, 48），所以单次 LLM 最坏耗时是正常值的 3 倍。

### 0.7 `compactAiMessageForMemory` 改的正是「对话正文」

它按阈值（约 2400 字符）把 AI 正文替换成"关键代码片段摘要"（`ChatHistorySchemaMigrationSupport.java:196-237`）。

**注意：这个函数不可逆，而且它处理的是 AI 正文，不是工具结果。** 设计里如果要立"某一层绝不改对话正文"这种规矩，得先说清它跟这个函数的关系——不能一边说"绝不改正文"，一边把它归到"已有能力"里。

### 0.8 `cm:ref` 归档有个分叉 bug

`refId = sha256(relative + ":" + content前2000字符)`（`core/memory/ConversationMemoryRefArchiver.java:60-62`）——**只哈希前 2000 字符**。写库用 `insertIgnore`（line 66），Redis 用 `set` 覆盖（line 87）。

所以同一路径下"前 2000 字符相同、尾部不同"的两版内容，refId 相同 → MySQL 留 v1、Redis 是 v2；3 天后 Redis 过期回源，读到 v1。**真相源与热缓存静默分叉。**

另外读回链路**未实现**（`TODO(memory-v4)`，line 68）。

## 1. 设计目标（这些是已定的，不要重新论证）

### 1.1 分层，从便宜到贵

用户已经确定采用**四层自动链 + 两个附属**的结构：

| 层 | 定位 | 花不花钱 | 花不花时间 |
|---|---|---|---|
| 第 0 层 结构性排除 | 东西根本不让它进上下文 | 不花 | 不花 |
| 第 1 层 确定性清理 | 已进来的，做无损降级 | 不花（零 LLM） | 不花 |
| 第 2 层 轻量裁剪 | 擦掉保护窗口之外的工具输出 | 不花（零 LLM） | 不花 |
| 第 3 层 摘要 | 切段 + 写摘要 | **花钱** | **70~100 秒** |
| 附属一 后台异步 | 把第 3 层的**计算**提前 | 花钱（照花） | **不占用户时间** |
| 附属二 手动压缩 | 用户按按钮走第 3 层 | 花钱 | 花时间 |

### 1.2 三条铁律（硬约束，不许破）

1. **不许越层**：第 1 层能解决就不许用第 2 层，第 2 层能解决就不许用第 3 层。
2. **不许倒序**：先降级（内容还在、只是变短），再擦除（内容换成占位符）。反过来会丢掉本来能保住的东西。
3. **不许碰不该碰的**：每层都有明确的"绝不"清单（见 2 节表）。

**并且**：任何会丢内容的层，都要在丢掉的地方**留痕**（"这里原来有东西"），不能静默抹掉。

理由（这是设计里最贵的一类错误）：不是"丢信息"，而是"**丢了我不知道**"。一个带着「未经验证」标记的猜测被压缩后变成语气确定的事实，标记消失，模型开始拿它当定论用。

### 1.3 附属一的核心设计（已定）

**后台做的是「素材」，不是「成品」。**

这是关键区分：后台跑的时候**还不知道将来的切点在哪**（切点必须等到触发那一刻才能定，因为那时才知道要保留最近多长一段）。所以：

| | 什么时候做 | 产出 |
|---|---|---|
| **后台** | 占用到后台触发点，且距上次更新够量 | 一份持续更新的**会话状态快照** + 一个「**我算到哪条**」标记 |
| **前台** | 触发压缩时 | 拿快照当**骨架** + 从标记处往后**补保留段** = 最终摘要 |

**后台省的是"读旧内容"，切段和组装仍在触发时做。所以它省的不是全部。**

### 1.4 附属一的失败兜底（硬规则）

**素材必须自带两个标记，前台不信没有完整标记的素材。**

```
后台写回素材时，必须同时写入：
  computed_through   → 我算到哪一条了
  status             → success / failed / empty

前台取素材时：
  ├─ 缺 computed_through        → 不许当骨架用，现场算
  ├─ status 不是 success        → 不许当骨架用，现场算
  ├─ 素材落后太多               → 不许当骨架用，现场算
  └─ 标记完整、成功、不旧        → 当骨架用，从 computed_through 往后补保留段
```

**价值**：后台可以随便失败，前台永远不会因此丢东西——失败只是退化成"现场算"。

**注意这条的边界**：它防的是"标记缺失"，**防不住"摘要是空的但被洗成占位符"**（见 0.2）。0.2 必须单独修（见第 4 节）。

### 1.5 会话状态快照 vs 跨会话持久记忆，必须分开

**这是两份不同的东西，别混成一份「知识库」。**

| | **会话状态快照** | **跨会话持久记忆** |
|---|---|---|
| 生命周期 | **会话结束即弃** | 跨会话保留 |
| 内容 | 这次干了什么、干到哪、下一步 | 用户偏好、项目约定 |
| 谁维护 | 后台自动更新 | 模型主动写，用户可编辑 |
| 压缩时 | **当摘要骨架用** | **从磁盘重新注入，不进摘要** |
| 上限 | 要有硬顶 | 要有硬顶 |

**混在一起的后果**：这次任务的临时噪声（半成品路径、未定的决策、试错假设）会渗进**所有后续会话**。

**本次设计只做前一份（会话状态快照）。**

### 1.6 快照的更新频率必须节流

**不是"每次对话结束都更新"。** 三个理由：

1. **钱**：每轮一次模型调用，跟"压缩是为了省钱"直接冲突。
2. **缓存**：每轮重写已发出去的内容，会每轮破坏供应商的缓存前缀。
3. **质量**：每轮只看增量改，模型看不到全局，改十轮后文档会自相矛盾。

**参照值**（Claude Code v2.1.88 的 session memory，三个默认值）：
`minimumMessageTokensToInit = 10000` / `minimumTokensBetweenUpdate = 5000` / `toolCallsBetweenUpdates = 3`。

（**注意**：这三个数出自 v2.1.88 的镜像源码；在当前发行版 2.1.268 里这三个符号 **0 命中**，所以它们是**参考值不是现行值**。）

### 1.7 快照的更新方式：重写整份，不是打补丁

打补丁（差量）省 token，但会**累积漂移**——每轮只看到增量改，改十次后前后矛盾。而且这份快照本身有硬顶（规模可控），重写的成本是可以接受的。

**一致性和省 token 之间，选一致性。**

### 1.8 快照必须是派生视图，不是真相源

**MySQL 是真相源。** 快照必须能**从对话记录 + 数据库重建出来**。

定位写死：它坏了、丢了、写歪了，重建一份就行，不影响真相源。否则你会得到两份权威状态，然后出现"文档说 A、数据库说 B"这种极难查的 bug。

## 2. 各层的边界（要写进方案的"绝不"清单）

| 层 | 什么时候动 | 动什么 | **绝不做什么** |
|---|---|---|---|
| 第 0 层 | 东西**进上下文之前** | 按预算截断；超阈值的外置并留引用 | 绝不动已经在上下文里的东西 |
| 第 1 层 | 压缩时，先于第 2、3 层 | 去重；旧内容降级；参数截断 | 绝不调 LLM；绝不改对话正文 |
| 第 2 层 | 压缩时，在第 1 层之后 | 擦掉保护窗口之外的工具输出，替换成占位符 | 绝不调 LLM；不够门槛绝不提交 |
| 第 3 层 | 占用 ≥ 阈值 | 切 head / summary / tail；写结构化摘要 | 前面能解决就不许调；绝不切开 tool 调用/结果对；绝不动最新一条用户消息 |

> 第 0、1、2 层的具体作用对象**取决于第 4 节的问题 1 的答案**（工具结果到底活在哪个集合里）。不要先假定。

## 4. 必须先解决的前置问题（不能跳过）

这几条是**核验时从本仓库源码里发现的、原设计漏掉的**。在它们有答案之前，分层设计会悬空。

### 问题 1：工具结果到底活在哪个集合里？

见 0.1。工具结果不落 `chat_history`，重建时消失，只可能在 Redis 热窗口（TTL 600 秒）里。

**要回答**：
- 第 0/1/2 层的"工具结果"作用对象是什么？（LangChain4j 的 in-flight 消息列表？还是要把工具结果落成新的消息类型？）
- 如果工具结果只活在 10 分钟 TTL 的 Redis 里，压缩该挂在什么时机？
- 现有 `compactAiMessageForMemory` 改的是 AI 正文——如果立"某层绝不改正文"的规矩，跟它怎么共存？

### 问题 2：摘要为空必须先被拦住（0.2 那个 bug）

现有 `parseSummaryResponse` 会把空洗成占位符，然后被当成成功落库。**任何基于"检查摘要非空"的兜底都拦不住它。**

**要回答**：空判定打在**原始模型输出**上（parse 之前），`status=empty`，绝不落库。这条路径单独改。方案里要写清改哪个函数、改成什么。

### 问题 3：LLM 调用必须移出事务（0.3）

现在是 `@Transactional` 里 `while(true)` 每轮一次 LLM 调用。搬到后台线程会：一个后台任务持有 MySQL 连接 1.5 分钟以上，并发起来耗尽连接池，主生成请求超时——**用户看到"生成失败"，原因跟压缩毫无关系**。

**要回答**：先算后开事务落库；循环加上限（单次最多合并 N 次）；后台用独立线程池、限并发，不与主生成抢池。

### 问题 4：「窗口」这个数从哪来（0.5）

全仓没有上下文窗口配置。要按"占用 / 窗口 ≥ 比例"做阈值，得先把窗口落成配置。

**要回答**：
- 窗口作为显式配置落到 6 个模型配置里（`application.yml` 的模型段）。
- 闸门改用**上一轮响应的 `inputTokenCount`**——这个数据已经在 `AiModelMonitorListener.java:107-113` 里取到了，只是没接到控制流。**接过来，不要另造字符估算器。**

### 问题 5：先量化"每轮摘要"的现状成本（0.4）

现有压缩是每轮触发的固定税，不是罕见事件。100 轮会话 ≈ 100 次额外摘要调用。

**要回答**：统计现网每轮摘要的调用次数与 token，再决定引入第 3 层值不值。**这是最该先做的一件事。**

### 问题 6：供应商到底有没有前缀缓存（0.6）

平台跑的是 DashScope compatible-mode（qwen 系列），**不是 Anthropic**。而"后台请求 fork 主会话以复用缓存前缀"这个优化的经济性，**建立在"供应商提供前缀缓存"这个未经验证的假设上**。

**要回答**：先实测该端点是否返回缓存命中字段（如 `prompt_cache_hit_tokens`）。**如果不提供，"后台 fork 复用前缀"省的那部分根本不存在**，后台请求就是一次全额全量调用。设计不该建立在一个未验证的供应商特性上。

## 5. 已知陷阱（核验时挑出来的，方案里要显式处理）

按严重程度排，前三条会导致静默丢数据或静默烧钱。

**P1｜异步路径天然违反"不许倒序"。**
后台在 50% 读的是**未剪枝**的历史，前台在 75% 用**已剪枝**的历史组装。骨架里描述的内容（被擦掉的工具输出）在最终上下文里已不存在；反过来前台真正保留的部分骨架里没有。模型会引用看不见的东西。
→ 素材必须记录「**它基于哪一版历史**」（epoch / 版本号），前台只在版本一致时复用。

**P2｜第 0 层的截断会让第 1 层的去重把不同东西并成一个。**
如果第 0 层把超阈值内容换成"指针"（`cm:ref` 形态），第 1 层对内容做等值去重时，两条指向**不同 refId** 的指针文本长得一样 → 判定重复删掉一条 → 被删的内容再也取不回。
→ 去重 key 必须用指针里的 refId / 内容哈希，**不是指针文本本身**；带 ref 的消息标记为不可去重。

**P3｜第 3 层永远拿不到第 2 层擦掉的信息。**
第 2 层先把保护窗口外的内容换成占位符，第 3 层再对"最早那几摞"摘要 → **摘要的输入是占位符** → 摘要是空壳，但 token 确实降了，"检查 token 有没有降"这个校验**会通过**。
→ 第 3 层的输入要基于"擦除前"的快照（或在摘要 prompt 里把占位符翻译回原文）；校验不能只看 token，要加"摘要里有效内容占比"这类检查。

**P4｜摘要预算超过摘要模型的输出上限。**
摘要是 `qwen3.6-max-preview`，`max-tokens: 8192`（`application-local-a.yml:33-36`）。如果按 Hermes 抄上限 10,000 token，**会被中途截断，而截断后仍被当成完整摘要落库**。
→ 摘要预算上限必须 ≤ 摘要模型的 `max-tokens`；或换输出上限更大的模型。

**P5｜"不能压缩"在现有代码里没有任何兜底。**
现有代码只按"未合并轮数 >2"判停（`ChatHistoryServiceImpl.java:831, 844`），**没有任何 token 检查**。滚动摘要每次吸收一轮、体积单调增长，而 `replaceConversationSummary` 不设大小上限（line 896）。摘要滚到接近原文时，每轮都白摘一次。
→ 加"压缩后 token 未降则标记无效并熔断"+"摘要长度硬上限"。

**P6｜按条数淘汰会切断 tool 对。**
`MessageWindowChatMemory.maxMessages = 160`（`ChatHistoryConstant.java:22`）按**条数**逐条挤出最早消息，**不识别 tool 对**。OpenAI 兼容端点会拒收"有 tool 结果但缺对应 tool_calls 的 assistant 消息" → 400。用户看到"生成失败"，看不出跟压缩有关。
→ 淘汰以「**轮 / tool 对**」为单位，不以单条为单位。

**P7｜`cm:ref` 的 refId 只哈希前 2000 字符（0.8）。**
同路径下前 2000 字符相同、尾部不同的两版内容会得到同一个 refId → MySQL `insertIgnore` 留 v1、Redis `set` 覆盖成 v2 → 两处静默分叉。
→ refId 用全文哈希；或 `insertIgnore` 改 upsert；或读回时校验长度/哈希。

**P8｜`computed_through` 锚点可能悬空。**
现有 `removeLatestFailedAiMessageForRetry`（`ChatHistoryServiceImpl.java:950` 起）会从 Redis 尾部删消息。如果锚点指向的那条被删了，"从标记处往后补保留段"会从一个不存在的锚点拼接。
→ 前台取素材时必须验证锚点仍可解析，否则现场算。

**P9｜写回要防"更旧的覆盖更新的"。**
后台在 T0 读（标记 N0），前台在 T1 完成压缩并写了 N1，后台在 T2 写回 N0 → 下次前台**信任这个更旧的标记**，静默回退。
→ 写回用 CAS：仅当 `computed_through > 已存标记` 才接受；加 epoch 字段。

**P10｜后台任务的锁与 TTL。**
- "正在跑"标记必须用 `SET NX EX`，且 **TTL 要大于最坏运行时长**（含全部重试：模型 `max-retries: 2`，最坏是正常值的 3 倍）。
- 进程在 set 与 clear 之间崩溃会把标记永久卡住 → 后台从此再也不跑，**静默退化成"永远现场算"**，用户只觉得变慢。
- 三个字段（素材 / `computed_through` / `status`）必须**一次原子写**，否则崩溃后会落成"status=success + 旧素材"。

**P11｜"太旧就放弃"的判定基准。**
如果放弃线是"落后超过窗口 20%"，而后台在 50–55% 启动、前台在 75% 触发——**这中间正好跨过 20%**，放弃线卡在正常间隔上。会话走得快时大概率被判太旧丢弃，后台那次钱白花。
→ 判定基准改成"**后台完成时刻起又前进了多少**"，并让阈值明显大于"后台跑完所需时间内会话的增长上界"（Claude Code 2.1.88 用的是 **stale 阈值 60 秒**、消费时最多等 **15 秒**，可作参照）。

**P12｜小窗口上这套数字会自相矛盾。**
32K 窗口下：保护窗口 40,000 > 32,768 → **保护覆盖整个上下文** → 无可擦 → 永不提交；第 3 层下限 64,000 > 32,768 → **永不触发**。整条链静默失效，最后撞供应商上限报错，而报错原因跟压缩看不出关系。
→ 所有绝对下限改成 `min(绝对值, 窗口 × 比例)` 的形式。

**P13｜后台任务失败时是负收益。**
后台 50% 跑一次 + 前台 75% 因素材过期/失败又现场算一次 → 同一段历史摘要两遍，**全量输入 ×2**，比不做后台更贵。
→ 后台成功/失败计入成本指标；失败后前台现场算要设"本会话本小时最多几次"的上限。
