## 1. 定位与不可误解的边界

目标不是给工程贴“企业级”标签，而是让用户知道：哪些业务要求已验证、哪里失败、什么没有测、哪些证据能够复现。测试与后续独立开发步骤共同帮助 Demo 逐步满足实际交付要求。

产品差异化应来自项目专属测试、最终业务状态检查、版本化证据和复测闭环，不是模型措辞、工具数量或单一综合分。本轮没有证明能力超过 Codex / Claude Code，不把竞争目标当作已达成结论。

### 1.1 用户已确认的约束

1. 平台基准、Agent 项目个性化测试、自然语言定制测试三者并存；不只并发/QPS。
2. 用户面向各类项目；环境不支持时如实说明，不暗接用户电脑、远程机器或生产系统。
3. 同一聊天框、同一套 Agent 能力。开发与测试是具体任务的内部职责状态，不要求用户操作模式切换器；工作台可展示测试清单、进度和证据。
4. 测试任务只测试，不自动修改业务源码；生成测试代码、夹具、规则属于测试能力，不能借机修业务代码。
5. 首次默认勾选 Agent 推荐的基础必测及高风险业务项；再次默认上次未通过项加改动影响项，用户可调整。列表完整展示，不选择不等于通过。
6. 适用的必要细项均需达标，综合分不能抵消任何必要项失败或未验证；用户取消必要项仍保留未验证标记。
7. 本轮针对独立代码快照；用户可同时继续开发。报告绑定旧版本时不能代表当前工作区。
8. 执行中新增风险先建议，用户确认后才测试；未执行的新风险也必须进入报告。
9. 本轮验收标准固定，标准修改下轮生效；通用模板版本固定，新版由用户主动升级，不改历史结论。
10. 测试代码和用户实际项目代码隔离；可强制取消，先弹窗提示影响，不以点击取消或关闭聊天连接等同停止成功。
11. 本轮所有选中项结算后汇总一份报告；报告可查看，默认不永久保存完整报告，主动“下载报告”同时保存到当前项目。不能自动保存一堆业务文件。
12. 用户可手动或在对话中修改方案；项目专属测试不自动升级成通用模板，通用模板在独立模板管理入口制作，可见范围复用已有应用规则。
13. 不以金额/Token 预算决定是否跳过必要测试。执行权限、资源保护、无进展停止和用户取消仍有效，保护限制不能冒充测试通过。
14. 可配置报告导出与修复建议行为，但本轮报告未通过时同样要展示；自动导出不等于自动永久保存，自动生成修复方案不等于自动执行修复。
15. 后续修复须用户授权，默认包含相关已选项回归；旧报告问题先在最新版本复现。完整修复闭环与代码/上下文回档属于第三项专项设计。

### 1.2 首期不承诺

- 不承诺所有程序都能在通用 Docker 环境运行；手机设备、专用硬件、GPU、特定操作系统、外部服务等有明确环境需求。
- 不颁发企业级认证，不替代业务负责人、运维或合规验收，不默认发布生产。
- 不内置所有开源工具，不默认上云 SaaS，不自动连接生产数据库、真实支付或邮件系统。
- 不开发另一套聊天助手，不新增用户必须理解的 Agent 模式状态机界面。
- 不把平台自己的 JUnit/pytest/Vitest 测试直接当成用户导入项目已经测过。

## 3. 用户流程与前端评审范围

1. 用户在原聊天提出测试要求；Agent 读取当前项目合法文件与已有规则，列项目事实、未知项和必要的业务问卷。只问无法从代码确认的业务决策，例如允许的角色、重复订单含义、目标环境，不让用户猜技术事实。
2. 工作台展示完整测试清单：名称、类别、适用性、必测标记、默认选中原因、前置条件、验收标准和上次结果。高级证据按需展开，默认文案简洁。
3. 用户勾选并确认执行。本轮冻结标准与模板版本，建立一致快照；依赖缺失时按导入约定请求安装确认，不自动在导入后安装或运行。
4. 执行期间显示阶段、已结算/未结算项和错误，原聊天仍可用于开发；不把开发输入发送给后台测试，也不让后台任务修改当前代码。
5. 新风险显示“待确认测试”，不擅自执行。若用户确认，本轮追加独立授权记录，标准不变并使用同一快照；需要新版本或新标准的另开轮次。
6. 已选项全部得到终态后汇总本轮报告，包括无法执行项。取消也生成不完整摘要，不能等到全绿才显示结果。单项失败不会静默取消无依赖的其他项；依赖失败的项显示阻塞，不伪装测试失败或通过。
7. 用户主动保存/下载报告或请求修复方案。报告里的修复建议不能直接触发源码写入。

前端先单独评审：同一聊天、完整勾选列表、旧版本徽标、失败证据、新风险确认、取消弹窗、报告下载、模板升级提示、窄面板与深浅主题。评审只使用明确标记的样例状态；静态图或模拟事件不能当真实测试完成。

“独立模板界面”仅用于管理复用资产，不是另一套测试对话。入口位置在前端评审时按已有信息架构确定，不在本轮擅自新增全平台公开市场。

## 4. 最小侵入式架构建议

```text
原聊天 + 右侧测试面板
  Java：应用鉴权、测试方案、授权、快照、轮次/资源台账、证据校验、报告
    现有 NDJSON / Python Worker 池（扩展契约，旧能力保持）
      同一 Agent 装配能力：规划/测试任务状态、专属可检索上下文
      测试执行适配器：JUnit / pytest / Vitest / Playwright / 其他候选
        本轮专属 Docker 执行环境、测试夹具、服务与数据卷
    程序化结果归一与判定（Agent 不能自行改通过状态）
```

不新增 Python HTTP 服务、图数据库、消息中间件或微服务。建议 Java 独立 `acceptance` 包承载新增业务；服务命名为草案，不代表文件已存在。

- `AcceptancePlanService`：测试列表、规则来源、适用性、版本与用户选择。
- `AcceptanceRunService`：快照准入、轮次状态、执行调度、取消、回收、幂等。
- `AcceptanceEvidenceService`：命令/原始输出采集、适配器校验、结果归一、版本资格核验。
- `AcceptanceReportService`：最终汇总、短期可查看、主动下载并保存项目。
- 现有 Agent worker 仍承担模型执行，不新增独立“测试 AI”。纯框架执行可走同一 Python 执行面内的适配器，不要求每一步都调用模型。

### 4.1 隔离与允许写入的位置

建议由 Java 路径服务分配 `temp/acceptance/{appId}/{testRunId}/`，下含 `source/`（不可变快照）、`runner/`（可运行副本）、`tests/`（测试代码）、`artifacts/`（输出）。不使用当前 `temp/code_output/project_{appId}` 作为测试命令的读写挂载源。

- 源项目与 source 无共享可写 inode：不以硬链接假装隔离；处理符号链接、Windows junction、大小写和跨目录逃逸。
- source 内容清单含相对路径、完整内容 hash、必要执行权限及排除原因。保存 wrapper、锁文件、测试/运行配置、需要的资源；不能沿用知识快照的截断规则。
- `.glyahh/run.json` 等确需运行的项目配置要单独纳入输入清单；平台生成日志、旧报告、保护备份不能因同在 `.glyahh` 就混入源码或模型上下文。测试快照、回档快照和知识快照有不同用途，不默认共用相同排除集。
- 建快照时短暂进入应用写入协调，同时覆盖平台手动保存和 Agent 写入；先后扫描与复制清单一致后才发布 source。若有未受协调的外部写入导致不一致，重建或明确失败，不发布混合版本。长时间测试不持有开发锁。
- 测试 Agent 读取 source，只能写 tests/批准的夹具。框架可在 runner 内创建构建产物、缓存与临时数据，但不允许将业务源文件变化当测试修复；前后校验业务输入清单，发现漂移记 ERROR 并留证。
- 某些框架要求测试进入源码树：仅在 runner 叠加映射到 tests 的生成测试文件，清单分别记录原始源码与 harness；不改变 source 或用户当前项目。
- 自动格式化、lint `--fix`、代码生成及安装脚本均可能写源码。先分析真实脚本和权限需求；需要改变业务输入的任务不能伪装为测试批准。
- 工作区检查与 Shell 权限必须执行侧强制，不能仅依赖提示词、命令字符串黑名单或事后 diff。

### 4.2 并行开发、容器与数据隔离

保留开发任务的 app 写入串行化；隔离测试走自己的准入与资源登记，绝不能直接调用无协调入口就宣称并发安全。容器/端口/卷/进程以 `testRunId` 标识，不以 appId 覆盖预览容器。

不复用主聊天的 checkpointer thread 或已有开发 session 容器。测试子执行可用 `app:{appId}:test:{testRunId}:{contextEpoch}` 作为内部 thread，用户仍只看到同一聊天；这不是独立产品助手。

测试使用独立数据库/夹具/缓存命名空间，不能连接平台 `biz` 库、当前开发实例或真实外部系统。没有可隔离环境时相关项 BLOCKED/UNSUPPORTED，不自动删数据或改用用户环境。标准业务状态观察器负责核对真实行数、状态与资源，不只看 HTTP 200。

Docker 不可用时明确失败，不落回 `local_shell` 执行导入项目。无 docker.sock、宿主凭据、特权、host 网络和任意宿主挂载；安装出网与测试访问范围分开授权，外部请求目标及重定向需校验。具体防护必须实际测试，不把 Docker 名称当绝对隔离证明。

CPU、内存、PID、磁盘、日志大小、超时及并发限制来自执行环境安全配置，不是“金额预算”。不得按耗费 Token/金额静默跳项。现有 30 分钟/60 次模型调用不能直接移植为验收承诺；上线前公开实际执行保护限制，触发时标明未完成，不能缩小测试冒充全通过。

## 5. 测试内容、适用性和测试质量

### 5.1 三类规则来源

| 来源 | 输入与作用 | 约束 |
| --- | --- | --- |
| 平台基准模板 | 固定版本的通用检查/运行器/指标规则 | 对用户项目做适配，不复制漏洞样本进用户工程；没有环境或预期无法执行 |
| 项目专属测试 | 当前源码、接口契约、用户业务回答，由 Agent 生成 | 带生成依据和测试代码 hash，不自动公开或跨项目复用 |
| 用户通用模板 | 在模板管理界面制作并显式用于项目 | 版本固定、归属/可见性复用既有规则，更新由项目主动升级 |

项目已有测试首先复用；运行其配置前确认外部依赖、副作用和适用性，不能因现有测试为绿就保证足够覆盖业务。

### 5.2 按风险组织清单，而不是统一塞满工具

| 类别 | 检查目标举例 | 证据形式 |
| --- | --- | --- |
| 基线与构建 | 依赖、配置、可复跑入口、真正启动/退出 | 命令、锁文件/镜像版本、退出码、就绪与输出 |
| 业务与端到端 | 主流程、失败路径、最终业务状态 | 输入、预期/实际、页面 trace、数据库或文件状态 |
| 权限与校验 | 角色、越权、输入边界、异常响应、敏感信息 | 角色矩阵、测试请求、响应及最终状态 |
| 一致性与重复请求 | 幂等、事务、重复事件、部分失败 | 前后状态、并发输入、数量/不变量断言 |
| 资源与可观测性 | 连接释放、进程退出、日志、错误定位 | 受控故障、资源采样、日志关联与清理结果 |
| 配置与交付条件 | 缺配置、环境依赖、运行说明与回退依据 | 环境需求、检查结果、用户声明与未验证范围 |
| 并发与性能 | 业务相关延迟、错误率、吞吐、瓶颈 | 声明负载模型、预热、时长、样本、资源规格 |
| 依赖与静态风险 | 已知缺陷、泄露、许可证/供应链线索 | 规则/数据库版本、匹配位置、误报核验 |

最后一行属于风险线索，不自动宣称漏洞可利用或法律合规。选型与许可证需按实际部署方式另行核对，不默认购买第三方服务。

适用性为 `APPLICABLE / NOT_APPLICABLE / UNKNOWN`；必须带理由、依据、确认者。用户问卷是业务声明，不自动算机器验证；因环境缺失而不能跑不等于不适用。必要项不能被 Agent 为了拿高分改成不适用。

首次、复测的默认勾选只是推荐；旧版本通过项不自动记成本轮 PASS。无法可靠推导影响范围时建议扩大测试，不隐藏遗漏。图谱未就绪可用当前源码定位，不能虚构确定调用关系；这是独立测试任务读取源码，不是将图谱补全失败偷偷发布为成功。

### 5.3 防止“Agent 写测试又自己给分”

- 验收标准来自用户已确认预期/固定模板，不能直接从当前实现反推“正确答案”。
- 测试用例必须有输入、独立预期、断言及最终观察点。`assert true`、只看页面能打开或只检查 HTTP 200 不足以验证业务。
- 有真实缺陷的用例需证明能在缺陷版失败；适配器和生成测试质量可用有已知答案的正负样本/受控变异验证。此质量检查须在测试计划中声明，不能私自扩大用户项目执行范围。
- Agent 可以补充解释、定位候选与不确定性；PASS/FAIL 由已声明断言、原始结果解析和业务观察器决定。Agent 不能写入权威判定表或修改标准。
- 仓库、测试脚本和输出均不可信：项目可能伪造 JUnit 报告，模型也可能被日志指令诱导。采集器在受管执行边界记录事实、校验产物来源；关键业务观察和基准答案独立于生成测试。文件 hash 只证明内容一致，不能证明测试诚实或语义正确。
- 重试保存每次结果，首次失败后再绿标记不稳定；不得用最后一次覆盖失败。代码/标准/模板变化另开轮次，基础设施重试保留同轮 attempt 并说明理由。

## 6. 验收结论与评分建议

下面是可审阅的程序判定建议，不是行业统一企业级公式；上线前需对固定样本校准，权重不得由每次 Agent 临时调整。

### 6.1 三个轴分开

1. **执行状态**：任务是否完整运行、取消、出错。
2. **测试结果**：每条断言是否满足，是否不稳定或无证据。
3. **版本/覆盖资格**：哪些必要项未测，结果是否适用于当前代码和上下文边界。

本轮收尾成功可以包含 FAIL：收齐失败证据并报告是执行完成，不是项目验收通过。UI 显示“测试完成 · 存在失败”，不能只展示 succeeded。

必要门槛建议：所有适用必要项均有本轮合法版本证据且 PASS；不存在阻塞验收的新高风险未验证项；标准/上下文/权限/最终业务观察有效。任一 FAIL 则未达标；无失败但必要项 NOT_RUN/BLOCKED/UNKNOWN/CANCELLED/FLAKY 则未完整验证。用户可以导出这些报告，不能导出为通过。

上述 PASS 对程序项由执行器判定；纯人工必要项按确认后的验收计划记录人工确认与证据，标明验证方式，不伪装为程序运行通过。人工未确认或附件缺失同样不能被综合分抵消。

全体选中项通过只显示“本次选中项通过”；没有明确完整业务验收范围时，不能扩大为“项目可上线”。标准修改或用户接受风险不追溯篡改客观结果。

### 6.2 用于辅助比较的三个分量

- 程序指标：逐项结果、目标值/实测值、覆盖范围。门槛全部满足后可展示达标余量等比较，不以统一 200ms、固定 QPS 或覆盖率承诺所有业务。
- Agent 执行质量：声明测试计划的证据绑定率、可复现步骤完整率、失败信息完整率；权限/版本/标准违规单独硬标记。分子分母和缺失项公开，零分母显示不适用，不允许模型自报高分。
- 用户问卷：目标环境、业务预期、角色、数据边界、人工验收确认等；标记声明来源与未验证部分，不把用户打勾升级成自动化证据。

可选综合展示建议为固定、版本化规则对标准化分量汇总，默认先呈现门槛、覆盖和分量，再显示辅助分。总分算法及权重需样本校准后单独冻结，首期不编造“85 分企业级”之类阈值。对外比较 Agent 能力另用平台已知答案样本，与用户项目验收隔离。

建议先落地以下可计算分量，不直接相加成企业级分数：

| 分量 | 分子 / 分母 | 缺失如何计 |
| --- | --- | --- |
| 必要项验证覆盖率 | 有本轮合法结果证据的适用必要项 / 全部适用必要项 | 未选择、阻塞、取消仍在分母；存在 UNKNOWN 必须另外显式阻断完整结论 |
| 必要项达标率 | 本轮合法 PASS 的适用必要项 / 全部适用必要项 | FAIL、FLAKY 及无证据不得进分子；门槛要求每项达标，不以平均值代替 |
| 执行证据绑定率 | 有命令、输入、版本、结果与安全证据引用的选中项 / 全部选中执行项 | 未执行或无效证据计缺失，不通过删除条目抬分 |
| 复跑信息完整率 | 复跑清单必填字段齐全的已执行项 / 全部已执行项 | 字段齐全只证明信息完整；真实重复运行的再现率单独计算，不混淆 |
| 失败信息完整率 | 含输入、预期/实际、原始错误或阻塞依据、版本与证据的异常项 / 全部异常项 | 无异常显示不适用；不以 Agent 文本解释代替原始错误 |

纯人工验收项独立记录用户确认与附件，标明验证方式，不伪造程序 PASS；是否属于该项目必要门槛由确认后的业务验收计划定义。
覆盖、达标与证据指标按程序/人工分组展示，不把用户声明算进自动化验证覆盖率。问卷未回答的必要业务预期为待确认，不让 Agent 自己填“是”。

新增风险确认通过独立 scope amendment 追加到原授权，保留初始 planRevision 与追加记录，不覆盖冻结标准；只在当前轮次仍可接纳执行时追加。轮次已经汇总完成、取消或失败，则确认动作创建新轮次，不重开旧终态或修改已导出的历史报告。

## 8. 状态机与失败收敛建议

### 8.1 轮次

```text
DRAFT -> READY -> SNAPSHOTTING -> PREPARING -> RUNNING
RUNNING -> COLLECTING -> SUMMARIZING -> COMPLETED
任一执行阶段 -> CANCELLING -> CANCELLED
执行/采集关键错误 -> FINALIZING_ERROR -> FAILED
停止未确认 -> STOP_FAILED（阻止继续使用或删除该任务资源）
```

`COMPLETED` 表示选中项全部结算及报告汇总完成，结果可包含失败。取消后只收集已有证据，不继续推进测试；失败收尾也不执行剩余测试。等待依赖/执行资源另记录原因与阶段，不能自动跳过并成功结束。

合法旧版本报告另标 `OUTDATED`；回档代次变化后旧任务结果为用户只读历史，不具有新会话发布/检索资格。历史证据仍存在不等于新 Agent 可读。

### 8.2 单项

`NOT_RUN / QUEUED / RUNNING / PASS / FAIL / ERROR / BLOCKED / UNSUPPORTED / CANCELLED / FLAKY`。

- `FAIL`：实际执行并违反断言；`ERROR`：运行器、采集或输入漂移导致无法可靠判定。
- `BLOCKED`：依赖、授权、配置、隔离环境缺失；`UNSUPPORTED`：平台当前无所需执行能力。
- `FLAKY`：同一输入版本与标准下结果不一致；默认不满足必要项门槛。
- 不适用是条目的适用性属性，不等于 PASS，不通过改状态清空分母。

### 8.3 失败处理

| 事件 | 收敛规则 |
| --- | --- |
| 快照不一致/缺必要文件 | 不启动；列缺口，重新建立一致输入，不能用截断副本冒充原项目 |
| 无模型密钥/placeholder | Agent 功能错误，不生成伪测试；独立确定性测试可按原计划运行，但 Agent 必要能力缺失必须呈现 |
| 安装、启动或服务前置失败 | 相关项阻塞；无依赖项可继续，安装/启动记录不能自动升级为业务通过 |
| Shell 非零、报告零用例、产物缺失/损坏、exitCode 与报告矛盾 | 保存原始事实，规则无法可靠判定时 ERROR，不按绿色文本猜通过 |
| 用例失败 | 保留实际输入、断言、最终状态与错误；继续其他可执行选中项，不偷偷改业务或标准 |
| 运行器基础设施重试 | 先记录原因与失败 attempt，确认副作用已隔离/可重放；无新证据不无限重试 |
| 汇总 Agent 出错 | 程序结果仍展示，报告汇总明确失败；不假装完整报告已交付，不用自评分填补 |
| 强制取消 | 弹窗后撤销任务执行资格，阻止新工具启动，杀/停实际容器和进程，核验停止后 CANCELLED；未确认则 STOP_FAILED |
| Worker/Java 崩溃 | 依台账核对真实任务资源，收敛孤儿；不能恢复旧模型上下文后盲重跑可能有副作用的测试 |
| 回档/应用删除/权限撤销 | 停止相关任务与资源，代次 fencing 拒绝旧结果；删除/清理不能跨 app/run，也不能删用户代码 |
| 磁盘/日志上限、超时/OOM | 显式资源错误与未完成范围，保存已采集证据，不触发主机 Shell 降级或谎称全测完 |

停止核验应检查任务资源身份与实际终态，不仅请求已送达。确认停止前不能释放为可复用环境；清理采用已验证绝对路径与归属，不跟随 symlink/junction，不删除未停止或用户正在保存的证据。

## 9. 报告、保留与上下文边界

一份报告包含：项目/代码/环境版本、选定与未选范围、必要项覆盖、标准和模板版本、每条实际结果、缺陷输入/预期/实际/复跑步骤/证据、Agent 推断与用户声明、新风险未验证项、不稳定/取消/资源异常、剩余风险与环境限制。

报告默认可在短期任务结果中查看，不永久落完整文件。为支持“上次失败默认勾选”保留最小结构化任务台账与用例状态；完整报告、源码快照、trace、原始日志设明确保留策略。此区别是工程建议，保留期限和容量必须在实现前明确并显示，不擅自承诺永久回放。

“自动导出报告”设置仅自动生成可下载产物；主动下载才保存项目。默认不自动导出，不自动永久保存。若用户要求开关同时自动保存，则改变已有保存边界，需单独确认，不能把两个动作混为一谈。

建议下载保存为 `.glyahh/reports/acceptance/{testRunId}/report.md` 与结构化 `report.json`；打包前脱敏，保存目标由服务端解析，CAS 校验项目身份和归属。按钮写“下载报告”，详情注明同时保存项目；项目保存失败不能显示“已保存”，允许重试，不因浏览器下载成功假称两步成功。

用户保存的报告不能任意篡改原始判定；用户备注与独立修复方案可以编辑，保留修订来源。原始产物过期后明确证据缺失，不能只靠摘要宣布可复现。秘密与隐私内容不默认进入报告或模型。

回档后，旧报告、失败台账、日志、测试会话 checkpoint、索引、用户保存的旧报告均可能污染上下文。Agent 只能检索当前 app/contextEpoch 下合法结果；旧报告只供用户只读查看，不因它放在项目目录就重新进入检索。复测默认选择也不得从被撤销分支读取“上次失败”。报告存储需可识别的独立平台目录和元数据，并与源码/图谱索引排除策略协调。用户显式授权旧内容恢复的产品规则交第三项设计，不默认为 AI 可读。

本节是未来实施计划，不是本轮执行命令。每一步独立验证，不一口气实现五项需求；窄样本跑通不代替本期全面验收。

| 阶段 | 交付内容 | 进入下一阶段的证据 |
| --- | --- | --- |

P1 建议样本是有明确业务规则的轻量服务，含一个可稳定复现的真实缺陷与已知正确预期；具体仓库、commit、依赖镜像、缺陷和许可证尚未锁定。不能先虚构某 Demo 通过数字。选择样本是研发调研工作，只有新增第三方成本或改变项目支持范围才询问用户。

第一条链路只做测试：导入能力未完成时允许用标明来源的内部样本验证执行器，但不得因此宣布导入功能完成。修复与补丁的完整重放留第三项独立阶段，不在测试任务中暗改源码。

## 11. 剩余风险和后续交付

- 成熟框架提供结果格式，不提供完整企业级认证；真实业务断言与运行环境仍需项目适配。
- 隔离快照需协调全部写入，当前 app 锁只保护 Agent，平台文件保存/其他后台任务必须纳入核对。
- 当前缺省 coding、placeholder、读写容器、断流取消与 session 容器复用均须在实现时明确改造，不能认为文档已修复。
- 默认非永久报告与最小台账、证据过期、上下文回档的实际接口需分别落实，避免历史结果重新污染模型。
- 评分权重、无进展检测、性能阈值、执行保护限制、证据保留期限需样本校准后冻结；不是逐个把工程参数扔给用户选择。
- 图谱定位能辅助影响分析，但全语言精确调用关系尚未验证；不能依赖一个未实现图谱承诺完整复测范围。
