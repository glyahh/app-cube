# 上下文压缩机制 —— 设计说明

> 这是一份**自包含的机制设计说明**，用于在设计阶段讨论、评审、迭代。
> 不含实现任务，不含本仓库的具体文件地址。读完之后你应该能完整理解这套机制是怎么运转的、以及每个设计选择是为什么。

---

## 一、要解决的问题

先讲清三件事，不然下面全是天书。

**一、模型不按「字」算账，按 token。** 英文约 4 字符 1 个，中文 1~2 字 1 个。

**二、模型面前有一张桌子，桌子是硬的。** 每个模型有一次能看的 token 上限，常见 200K，大的 1M。不是"看不清"，是根本看不见——撞上直接报错。

**三、每问一次，它都要把桌上所有的纸从头读一遍。** 模型没有记忆。每一轮请求都要把迄今为止的全部对话打包重发。

推论有两条：每轮的钱和时间正比于桌上纸的总量；而桌子只增不减。一个 agent 跑几十轮工具调用，必然撞墙。

所以整件事就是一句人话：

> **怎么让桌上的纸变少，又不丢"我们聊到哪儿了"。**

还有一条容易被忽略、但决定了整个机制形态的事实：**纸上东西越多，模型越不准。** 相关信息出现在输入的开头和结尾时表现最好，埋在中间会显著退化——这不是工程问题，是注意力的性质。所以压缩的正当性不只是省钱，而是：**同等信息量下，纸越少，模型越准。**

---

## 二、机制全貌

**四层自动链 + 两个附属。**

| | 是什么 | 会自己触发吗 | 花不花钱 | 花不花时间 |
|---|---|---|---|---|
| **第 0 层** 结构性排除 | 一层 | 会（内容进上下文前） | 不花 | 不花 |
| **第 1 层** 确定性清理 | 一层 | 会（压缩时） | 不花（零 LLM） | 不花 |
| **第 2 层** 轻量裁剪 | 一层 | 会（压缩时） | 不花（零 LLM） | 不花 |
| **第 3 层** 摘要 | 一层 | 会（超阈值时） | **花钱** | **70~100 秒** |
| 附属一 后台异步 | **不是层**，是第 3 层的优化 | **不会** | 花钱（照花） | **不占用户时间** |
| 附属二 手动压缩 | **不是层**，是第 3 层的入口 | **不会** | 花钱 | 花时间 |

**为什么后两个不算层**：因为它们不新增任何规则。后台异步只是把第 3 层的计算**提前做**，手动压缩只是给第 3 层**加一个按钮**——走的都是第 3 层那条流水线。

把这个数清楚很重要。如果把它们数成独立的层，它们就会各自带一套"什么时候该动手"的判定，然后跟第 3 层在同一个时刻抢着动手。

## 三、四层各自做什么，为什么这么排

### 第 0 层：门口的保安

**做什么。** 内容**还没进上下文**的时候，先在门口量一下：太长的砍短；特别长的，外置到别处（磁盘/文件），上下文里只放一个引用。

**为什么。** 因为内容一旦进上下文，**后面每一轮都要被重读一遍**。进门砍一刀只砍一次；进来之后再收拾，要收拾几十次。

**为什么排第一。** 它跟其他三层有个根本区别：**其他三层都在收拾已经进来的东西，只有它能让问题压根不发生。** 不让问题发生永远最省。

**边界：它绝不动已经在上下文里的任何东西。**

### 第 1 层：把废纸折小（零 LLM）

**做什么。** 已经进来、且**用过就不会再看**的内容（旧命令的输出、旧文件的片段），折成一行小字。完全一样的内容，留一份就够。旧图片降级成占位符，只留最新的几张。

**为什么。** 因为这一步**不需要模型、不需要花钱**——去重、截断、替换，都是确定性操作。

**既然不要钱，就在花钱之前先做完。**

**边界：绝不调 LLM；绝不改对话正文。** 正文是"我们聊到哪儿了"，是唯一丢了就找不回来的东西。工具输出丢了可以重跑一次命令，正文丢了就真没了。

### 第 2 层：把更旧的草稿纸扔掉（零 LLM）

**做什么。** 比第 1 层更狠：**擦除**（不是折小，是直接换成一句话"这里原来有东西"）。

**为什么它有两道硬约束，两道都不能少：**

**约束一：最近的那一段不许动。** 因为下一步最可能用到它。扔了它，等于你正要找笔的时候把笔扔了。

**约束二：够量才值得动手。** 这一条要想一下——**擦除会重写上下文的前缀，而供应商的缓存是按前缀匹配给折扣的**。前缀一变，折扣就没了，下一次请求要全额重算。

所以：**一次擦个大的，别一会儿擦一张。** 为了省两张纸就破坏缓存，省下来的不够亏的。

**边界：绝不调 LLM；绝不碰对话消息；不够门槛绝不提交。**

### 第 3 层：请人抄一遍（唯一花钱的）

**做什么。** 前面三层都做完了还是超阈值，才把**最早的那几摞**交给模型读一遍、写一张结构化摘要，夹在最上面。最近写的原样留着（逐字保留）。第一页（用户最开始说的话）永远留着。

**为什么排最后，两个理由都很硬：**

**一、它最贵。** 请模型写摘要，它得**把最早那几摞从头读到尾**——那正好是上下文里最多的部分。而且这时候上下文最满，等于**最贵的一次请求，发生在最贵的时候**。

**二、它一定会丢东西。** 把一摞纸变成几行字，一定有东西没写进去。所以能不写就不写。

**它还花时间。** 实测一次 70~100 秒，而且卡在用户最想继续干活的那一刻。

**边界：前面能解决就不许调它；绝不切开工具调用/结果对；绝不动最新一条用户消息。**

**附加要求：摘要必须是结构化的。** 字段固定、不能自由发挥。其中必须有"用户的约束/偏好"这一段，必须要求引用用户纠正的原话，必须写明"不要提及摘要或上下文压缩"。这些都是为了让摘要员知道什么该留。

## 四、附属一：后台异步

### 它省的不是钱，是时间

第 3 层贵在两处：**钱**（输入是被压缩的全部历史）和**时间**（70~100 秒的停顿）。后台异步**只解决时间这一样**，钱照花。

### 关键设计：后台做的是「素材」，不是「成品」

**这是整套设计里最容易做错的一点。**

一个自然的想法是"后台提前把前 N 条压好"。**这个想法是错的**，因为：

**后台跑的时候，还不知道将来的切点在哪。** 后台按"前 30%"压了，将来触发时可能只需要"前 20%"——那多压的 10% 就是白丢。而且会话在往前走，后台跑完那一刻的"前 30%"，过二十分钟已经不是同一个 30% 了。

**切点必须等到触发那一刻才能定**，因为那时候才知道要保留最近多长一段。

所以拆成两半：

| | 什么时候做 | 产出什么 |
|---|---|---|
| **后台** | 占用到后台触发点，且距上次更新够量 | 一份**持续更新的会话状态快照** + 一个「**我算到哪条**」的标记 |
| **前台** | 触发压缩时 | 拿快照当**骨架** + 从标记处往后**补保留段** = 最终摘要 |

**后台省的是"读旧内容"那部分。切段和组装仍然在触发时做。所以它省的不是全部。**

### 快照的更新频率必须节流

**不是"每轮更新"。** 三个理由：

1. **钱**：每轮一次模型调用，跟"压缩是为了省钱"直接矛盾。
2. **缓存**：每轮重写已经发出去的内容，会每轮破坏前缀缓存。
3. **质量**：每轮只看着增量改，模型看不到全局，改十轮后快照会自相矛盾。

**改成"够量才更新"**：占用涨了某个比例、或者隔了若干次工具调用。

参考值（Claude Code 的 session memory，三个默认值）：首次初始化要求积累 10,000 token、两次更新之间至少涨 5,000 token、至少隔 3 次工具调用。

### 快照的更新方式：重写整份，不是打补丁

打补丁（差量修改）省 token，但会**累积漂移**——每轮只看到增量改，改十次后前后矛盾。而快照本身有硬顶、规模可控，重写的成本可以接受。

**在一致性和省 token 之间，选一致性。**

### 快照必须有硬上限，而且它自己就是上下文的一部分

这一条容易漏。**快照最终是要进上下文的**（当摘要骨架用）。如果它无限增长，"用小文档代替大历史"就不成立了。

所以要有一个总量上限，以及**满了之后砍哪一节**的规则。按重要性砍，不是按时间砍。

参考值：单节 2,000 token、总量 12,000 token。

### 快照是「派生视图」，不是真相源

**数据库才是真相源。** 快照必须能**从对话记录 + 数据库重建出来**。

定位要写死：它坏了、丢了、写歪了，重建一份就行，不影响真相源。否则你会得到两份权威状态，然后出现"文档说 A、数据库说 B"这种极难查的问题。

### 会话状态快照 ≠ 跨会话持久记忆

**这是两份不同的东西，别混成一份「知识库」。**

| | **会话状态快照** | **跨会话持久记忆** |
|---|---|---|
| 生命周期 | **会话结束即弃** | 跨会话保留 |
| 内容 | 这次干了什么、干到哪、下一步 | 用户偏好、项目约定 |
| 谁维护 | 后台自动更新 | 模型主动写，用户可编辑 |
| 压缩时 | **当摘要骨架用** | **重新注入，不进摘要** |
| 谁维护 | 自动 | 半自动 + 用户可编辑 |

**混在一起的后果**：这次任务里的临时噪声（半成品的路径、还没定的决策、试错过程中的假设）会渗进**所有后续会话**。而且它看起来像"知识库"，容易被当成值得长期保留的东西。

### 失败兜底：素材必须自带两个标记

**这是整套设计里最重要的一条硬规则。**

后台是异步的，**它抄砸了你不会知道**。如果前台拿到一张抄砸的纸条当成好的用，丢的不是"最后一小截"，是"中间一整段"。

所以：

```
后台写回素材时，必须同时写入两个字段：
  computed_through   → 我算到哪一条了
  status             → success / failed / empty

前台取素材时：
  ├─ 缺 computed_through        → 不许当骨架用，现场算
  ├─ status 不是 success        → 不许当骨架用，现场算
  ├─ 素材落后太多               → 不许当骨架用，现场算
  └─ 标记完整、成功、不旧        → 当骨架用，从 computed_through 往后补保留段
```

**这条的价值**：后台可以随便失败，前台永远不会因此丢东西。失败只是退化成"现场算"——也就是不做后台时的行为，不是灾难。

**这条的边界**：它防的是"标记缺失"，**防不住"摘要是空的但被下游洗成了非空占位符"**。那种情况下标记会是完整的、`status=success`，这条检查全部通过，而丢的是中间一整段。**所以"摘要为空"必须单独在更早的位置拦——判定要打在模型的原始输出上，不是打在后处理之后。**

### 竞态：几个必须写死规则的时刻

后台在算的时候，会话在往前走。这几个时刻一定会遇到：

| 时刻 | 处理 |
|---|---|
| 后台跑完了，前台已经在压缩 | 素材写回但不用，下次再用。压缩以已经开始的那次为准 |
| 两次后台任务重叠 | 加"正在跑"标记，第二次跳过。否则两份素材互相覆盖 |
| 后台跑到一半，进程重启 | "正在跑"标记要有超时。启动时看到超时标记就当没跑过 |
| 后台在跑，用户按了手动压缩 | 不等它。手里有能用的就用，没有就现场算 |
| **后台写回时，前台已经写了更新的标记** | **写回要用 CAS——只接受比已存的更新。否则会静默回退到更旧的状态** |

**另两条容易漏的：**

- **"正在跑"标记的 TTL 必须大于最坏运行时长**（含全部重试）。设小了会重叠。
- **三处状态（素材 / 算到哪条 / 状态）必须一次原子写**。分三次写，崩在中间会落成"status=success + 旧素材"。

### 后台那个请求的前缀要和主会话一致

**如果后台请求用了不同的工具集、不同的 system、或者插了动态元数据（时间戳之类），前缀会在最前面就分叉，缓存一次都命中不了。**

而它要总结的正是**整段历史**（最满的时候）——那就是全系统最贵的一次调用，而且用户看不见。

**所以：任何"为了省 token 把工具定义裁掉"的优化，都是禁止的。**

（前提修正：如果供应商根本不提供前缀缓存，那这条不成立——但这意味着后台请求本来就是全额调用，"省缓存"那部分收益也不存在。**这个前提必须先验证，不能假设。**）

### 后台失败时是负收益

后台跑一次 + 前台因素材过期/失败又现场算一次 = **同一段历史摘要两遍，全量输入 ×2**。比不做后台更贵。

所以要：把后台的成功/失败计入成本指标；失败后前台现场算要设"本会话本小时最多几次"的上限。

### 设置项

| 设置项 | 默认 | 关掉之后的行为 |
|---|---|---|
| 后台异步整理 | **开** | **退回同步压缩**（不是关掉压缩） |
| 后台触发点 | 约 50–55% | 不适用 |
| 前台触发点 | 75% | 仍然生效 |
| 素材太旧的放弃线 | 见下 | 不适用 |

**「关掉之后的行为」是最容易写错的一格。** 用户把后台异步关了，压缩不能跟着失效，必须**退回同步**。否则用户关掉它之后，长会话直接撞墙，而撞墙的原因跟他的操作看着毫无关系。

**默认打开是对的**：同步阻塞意味着用户在最坏的时刻（上下文最满、最贵）等得最久。默认异步是更安全的默认值。

**关于"太旧的放弃线"**：不要用"落后超过窗口的某个比例"来判定，因为**后台启动点到前台触发点之间的间隔，正好就是那个比例**，淘汰线会卡在正常路径上，导致后台白跑。应该用"**从后台完成时刻起又前进了多少**"来判定，阈值要明显大于"后台跑完所需时间内会话的增长上界"。

参考值：Claude Code 用的是 **stale 60 秒**，消费时最多等 **15 秒**。

### 提醒的设计：知会，不询问

用户侧给提醒，但**提醒是知会，不是询问**——用户不需要点确认，压缩照常进行。

要明确让模型别跑去问用户"我们要不要继续"（有过模型反复确认"我们刚才在做什么"的问题）。

（"能撤销"是另一个功能，别跟"确认"混在一起。）

## 五、附属二：手动压缩

**走第 3 层完全相同的流水线**，只是入口不同。三条：

**一、优先用后台素材。** 有新鲜的就几秒搞定，没有就现场算。

**二、自定义指令必须显式拼进摘要 prompt。**

有一个实测值得记：用户把压缩指令写在配置文件里，**354 次触发里 0 次生效**（全部回落到内置模板）；改成内联写进命令里之后 7/7 生效。

所以"用户指定这次压什么"这个能力，必须**真的把那句话拼进给摘要员的说明里**，不能指望它从配置里自动被读到。

**三、按按钮的时机比按钮本身重要。**

任务换挡的时候按最省——那时缓存是热的。放一晚上再按，缓存早就过期了，得全额重算。

**所以别等写满了才按。** 在"这一段活干完了、要开始下一段"的时候按，这是人比机器强的地方。

## 六、三条铁律

违反任何一条，这套东西就会开始互相打架。

### 铁律一：不许越层

**第 1 层能解决就不许用第 2 层，第 2 层能解决就不许用第 3 层。**

前两层不花钱，第 3 层要花一次完整的大请求还搭上 70~100 秒。第 1 层已经把占用降回去了你还调第 3 层，就是白花钱加白丢信息。

### 铁律二：不许倒序

**先折小（降级，内容还在只是变短），再扔掉（擦除，内容换成占位符）。不能反过来。**

反过来你会发现，本来能靠折小保住的东西，已经被扔掉了。

### 铁律三：不许碰不该碰的

每一层都有自己的"绝不"清单（见第三节）。

这一条背后是个很实在的理由：**这套设计里最贵的错误不是「丢信息」，是「丢了我不知道」**。有过这样的实例：带着「未经验证」标记的猜测被压缩后变成了语气确定的事实，标记消失了，模型开始拿它当定论用。

**所以：任何会丢内容的层，都要在丢掉的地方留痕**（"这里原来有东西"），不能静默抹掉。

## 七、三个判定流程

**流程一：内容进上下文之前（第 0 层）**

```
有新内容要进来
  └─ 超过单条预算？
       ├─ 是 → 截断；超过外置阈值就写盘 + 留引用
       └─ 否 → 原样放进上下文
```

**流程二：到了该压缩的时刻（第 1 → 2 → 3 层）**

```
占用 ≥ 前台触发点？（自动）/ 用户按了按钮？（手动）
  ├─ 第 1 层：去重、降级旧内容、截参数、收旧图
  ├─ 还是超阈值？
  │    ├─ 否 → 停在这里，不调 LLM ✓
  │    └─ 是 → 继续
  ├─ 第 2 层：算一下「保护窗口之外有多少能擦」
  │    ├─ 不够门槛 → 跳过（不提交）
  │    └─ 够 → 擦掉，替换成占位符
  ├─ 还是超阈值？
  │    ├─ 否 → 停在这里，不调 LLM ✓
  │    └─ 是 → 继续
  └─ 第 3 层：切段 + 写摘要
       ├─ 有后台素材？
       │    ├─ 有，且标记完整、成功、不旧 → 当骨架用，从「算到哪条」往后补保留段
       │    ├─ 有，但太旧 → 放弃，现场算
       │    └─ 有，但标记缺失／状态是失败或空 → 放弃，现场算
       └─ 没有 → 现场算
```

**流程三：后台跑的时候（附属一）**

```
占用 ≥ 后台触发点？且距上次更新够久？
  ├─ 否 → 什么都不做
  └─ 是 → 发一个前缀与主会话一致的请求，整理「会话状态快照」
       ├─ 成功 → 原子写回：快照 + 算到哪条 + status=success
       ├─ 返回空 / 失败 → 写回 status=failed（**绝不能静默丢弃**）
       └─ 连续失败 N 次 → 熔断，停止后台任务，等恢复窗口到了再放一次探针
```

**三个流程里每一步「？」都是真检查，不是走过场。** 尤其是那两个"还是超阈值？"——检查必须用**供应商返回的真实 prompt token 数**，不是"消息条数变少了没有"。条数少但 token 没降太常见了（摘要本身可能很大）。

**而且要小心一种假通过**：如果第 2 层先擦掉了内容、第 3 层再对"已经变成占位符的那段"做摘要，摘要的输入就是占位符——**摘要会是空壳，但 token 确实降了，这个校验完全通过**。所以第 3 层的输入要基于"擦除前"的快照，或者校验要加一条"摘要里有效内容的占比"。

## 八、参考参数

**下面这些是别家的经验值，不是抄，是给你定自己数字时的锚点。每个数都要按本系统实测重新定。**

**特别注意单位**：下面 `2,000` 出现了两次（一次字符、一次 token），`40,000` 也出现两次（一次字符、一次 token）。中文 1~2 字/token、代码 3~4 字符/token——**单位混用会错一个量级**。

| 项 | 参考值 | 单位 | 抄自 |
|---|---|---|---|
| 单条内容进入上下文的预算 | 2,000 | **字符** | OpenCode / Cline |
| 外置阈值 | 40,000 | **字符** | Gemini |
| 降级豁免线（≤此值不动） | 200 | **字符** | Hermes |
| 调用参数截断 | 500 | **字符** | Hermes |
| 第 2 层保护窗口 | 40,000 | **token** | OpenCode |
| 第 2 层最小回收门槛 | 20,000 | **token** | OpenCode |
| 第 2 层永不擦的白名单 | 至少含"技能"类 | — | OpenCode |
| 第 3 层触发阈值 | 比例 0.50；小窗口抬到 0.75 | — | Hermes |
| 第 3 层逐字 tail | `max(10,000, min(25,000, 窗口 × 0.025))` | **token** | Hermes lean |
| 第 3 层摘要预算 | `max(2,000, min(内容 × 20%, min(窗口 × 5%, 10,000)))` | **token** | Hermes |
| 第 3 层头部保护衰减 | 第一次压缩后归零 | — | Hermes |
| 第 3 层熔断 | 冷却阶梯 (60, 300, 900) 秒 + 连续 2 次无效跳闸 | 秒 | Hermes |
| 快照单节上限 | 2,000 | **token** | Claude Code |
| 快照总量上限 | 12,000 | **token** | Claude Code |
| 快照首次初始化 | 10,000 | **token** | Claude Code（旧版） |
| 快照两次更新间隔 | 5,000 | **token** | Claude Code（旧版） |
| 快照更新间隔（工具调用数） | 3 | 次 | Claude Code（旧版） |
| 后台素材 stale 阈值 | 60 | 秒 | Claude Code |
| 消费素材时最长等待 | 15 | 秒 | Claude Code |

**两条与模型选择有关的硬约束：**

1. **摘要预算上限必须 ≤ 摘要模型的输出上限。** 否则摘要会被中途截断，而且截断后仍可能被当成完整摘要落库。
2. **摘要模型的上下文必须 ≥ 主模型窗口。** 它比主模型小的话，摘要调用会吃 context-length 错误、返回空，**中间那段就被无摘要丢弃**。这是公认的"压缩质量下降最常见的原因"。

**一条与窗口有关的硬约束：**

小窗口上，所有**绝对下限都会自相矛盾**。比如保护窗口设 40,000、第 3 层下限设 64,000，而窗口只有 32,768——保护窗口覆盖整个上下文，第 2 层没有可擦的东西；第 3 层下限比窗口还大，永不触发。**整条链静默失效**，最后撞供应商上限报错，而报错原因跟压缩看不出关系。

**所有绝对下限都要写成 `min(绝对值, 窗口 × 比例)` 的形式。**

## 九、已知的设计难点

按"会不会导致静默丢数据/静默烧钱"排。

**一、异步路径天然违反"不许倒序"。**
后台在 50% 读的是**未剪枝**的历史，前台在 75% 用**已剪枝**的历史组装。骨架里描述的内容在最终上下文里已经不存在；反过来前台真正保留的部分骨架里没有。**模型会引用看不见的东西。**
→ 素材必须记录「**它基于哪一版历史**」，前台只在版本一致时复用。

**二、第 0 层的外置会让第 1 层的去重把不同东西并成一个。**
如果第 0 层把超阈值内容换成"引用"，而第 1 层对内容做等值去重——两条指向**不同目标**的引用，文本长得一样，会被判为重复删掉一条，而被删的内容再也取不回。
→ 去重 key 必须用引用里的**标识或内容哈希**，不是引用文本本身；带引用的内容标记为不可去重。

**三、异步之后压缩变得看不见了。**
同步的时候界面卡一下就知道了。**异步之后压缩悄悄发生在后台——出错了用户完全不知道，只是突然发现模型开始忘事。**
→ 必须同时做三件事，缺一不可：给用户提示（知会不询问）、给用户设置开关（关掉=退回同步）、**给前台代码成功标记（这一条不能靠提醒替代）**。

**四、"摘要为空"有两条不同的路径，只堵一条不够。**
一条是"标记缺失"，被成功标记规则堵住了。另一条是"摘要被下游洗成了非空占位符"——这种情况下标记是完整的、状态是成功，**成功标记规则完全拦不住**。
→ 空判定要打在**模型的原始输出**上，不是打在后处理之后。

**五、"太旧就放弃"的判定基准容易选错。**
如果用"落后超过窗口的某个比例"，而后台启动点和前台触发点之间的间隔正好等于那个比例，淘汰线就卡在正常路径上。后台大概率白跑。
→ 用"从后台完成时刻起又前进了多少"。

**六、并发写回的单调性。**
后台在 T0 读（标记 N0），前台在 T1 完成压缩写了 N1 > N0，后台在 T2 写回 N0。如果直接覆盖，下次前台会**信任这个更旧的标记**，静默回退。
→ 写回用 CAS：只接受比已存标记更新的。

**七、三个字段分三次写会留下半截状态。**
分三次写、崩在中间，会落成"status=success + 旧素材"——**看起来完全正常**。
→ 一次原子写。

**八、多会话 / 多用户下的成本归属。**
后台任务花的钱算谁的？多个会话同时跑后台会不会互相影响？
→ 至少要把后台的成本计入指标，并在失败后限制前台的现场全量摘要次数。

## 十、设计阶段还没定的

- **这套机制的"窗口"从哪来**：需要先把上下文窗口作为显式配置落下来。如果系统里现在用的是"轮数"或"条数"做闸门，那"窗口 × 比例"里的窗口是没有来源的。
- **供应商到底有没有前缀缓存**：整套"后台请求复用前缀"的经济性论证建立在这个假设上。**必须先实测确认**——如果供应商不提供，后台请求就是全额调用，那部分收益不存在。
- **摘要模型的真实输出上限和上下文窗口**：这两条是上面那两个硬约束的输入，不能假设。
- **当前"每轮摘要"的真实成本**：如果现状是"每轮都滚一次摘要"，那它是一笔固定税，而不是罕见开销。**这个数要先量出来**，再决定引入第 3 层值不值。
