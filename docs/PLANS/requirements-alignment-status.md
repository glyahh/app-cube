## 2. 测试验收模式的整理边界

- 平台提供基准测试，Agent 可扫描当前项目并提出个性化测试；用户也可通过自然语言制作测试规则和程序。

- 适用的必要细项不能被综合高分抵消；未测与未通过需要显式呈现。不能凭 Agent 的自评分宣布整个工程达到企业级或可上线。
- 测试代码与项目代码隔离；测试任务不因发现问题自动修改业务源码。用户授权修改后，作为独立开发步骤执行，不要求先切换聊天界面或另一套 Agent。
- 可强制取消，取消前提示影响；设置和报告操作需要整理为明确交互。报告按用户主动下载/保存到项目的约定设计，不默认永久保存。
- 用户项目超出平台支持环境时如实报告，不默认连接用户电脑、远程机器或生产系统。
- 以上是已讨论的核心方向，不替代测试项适用性、开源基准选型、报告字段、评分依据和真实执行证据的专项设计。

- 测试清单、进度与证据仍可在已有工作台内展示；统一聊天不等于取消测试结果可视化，也不借此引入独立测试聊天系统。
- 测试发现问题不自动转成业务代码修改；修复是用户授权后的独立步骤。这一边界与同一个 Agent 同时具备开发和测试能力不矛盾。
- 用户批准修复时，默认包含修改后的针对性回归验证。修改和测试分别执行，自动复测相关的已选测试项；新增测试范围仍须用户确认。回归针对修复后的明确代码版本，保留修复前后的实际证据，不能把写入成功当作问题解决。批准界面或对话须明确说明包含回归验证，不改变首次导入不自动安装或运行的约定。
- 修复后的回归仍失败时，Agent 可以在已批准的修改与验证范围内继续定位、最小修复和验证，不要求每次失败后重新批准。无进展、需要扩大修改或测试范围、需要新增权限时停止继续尝试，报告实际证据并请求用户确认；不能无限重试、隐瞒失败、放宽本轮验收标准或绕过取消、权限与隔离约束。具体无进展判定与执行收敛机制仍待专项设计和验证。
- 修复最终仍未完成时，保留当前修改、失败现场和验证证据，展示修改差异、已通过及未通过项；用户决定继续修复或使用已约定的回档机制，不自动全部撤销，也不能宣称已完成或可交付。
- 测试报告对应旧代码版本，而当前项目已继续变化时，针对最新版本重新复现相关问题，再提出和执行修复；不默认在旧测试快照修完后合并回当前项目。旧报告保留为问题线索，不能当作最新版本的问题证据；问题已不存在时不机械修改。修复方案有实质变化时重新请求用户确认，回归结果绑定实际修复后的版本。重新复现同样须遵守已经授权的测试范围与执行权限。
- 后续需求访谈只询问会改变架构、权限、范围或用户体验的真实分歧；已确认规则、失败必须如实报告等基本原则不反复拆成选择题。研发可核实的事实与工程细节由研发自行调查，不转交用户猜测。

## 3. 回档的整理边界

- 回档针对用户消息执行前的快照；原提示词回填输入框，不自动发送。
- 先停止 Agent、工具、Shell 和后台任务，确认停止写入，保存保护状态，再执行恢复和验证；任何阶段失败不能显示成功。
- 回档提供保留用户修改与严格恢复两种选择。前者提取可保留修改并处理合并，后者按用户明确选择恢复目标状态；不能静默覆盖用户代码。
- 修改来源至少区分 Agent 生成、用户手动与用户明确认可，不只依据文件最后写入者；冲突不能自动吞掉，文本合并成功也不代表语义有效。
- 代码和模型上下文同步回档；撤销节点及后续上下文、摘要、工具结果与索引不得再进入当前请求。保护快照与旧分支仅供用户授权查看/恢复，不自动进入当前 Agent 检索。
- 不修改用户 Git 历史；快照、任务、上下文和项目版本必须绑定同一恢复目标。
- 首期回档范围仅为项目代码与 AI 上下文，不自动恢复项目数据库、数据或整个运行环境，也不触碰平台自身业务数据库或用户外部数据库。涉及数据库结构或数据变化时明确提示这一边界；发现恢复代码与当前数据库不兼容时，验证失败不能宣称恢复成功。项目沙箱数据库的一致性备份与恢复留作后续独立设计，不默认承诺。
- 专项草案已落盘：[开发衔接](./project-development-workflow-design.md)、[流程验收](./project-development-workflow-test-matrix.md)、[回档设计](./conversation-rollback-design.md)、[回档验收](./conversation-rollback-test-matrix.md)。状态机、停止、patch 来源、三方合并、失败恢复和真实请求核验仍待实施验证；不反复把工程常识作为用户选择题。
