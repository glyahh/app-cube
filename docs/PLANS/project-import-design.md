## 已确认

1. 五项后续需求按小步骤逐项推进，从简单到难、从表面到深入，不一次性实现全部。
2. 每个步骤独立确认、独立验证；初次访谈先对齐已有项目导入，后续按单项继续对齐，其余需求现状见共同文档总览，不将初次阶段措辞当作当前范围。
3. 项目导入支持两个入口：浏览器文件夹上传、Git 仓库地址导入。
4. 保留已有新项目生成能力；执行与调试保护原工程，使用隔离副本。
5. 需求和设计确认前不改功能代码，不启动服务或执行项目脚本。
6. Git 导入首期支持 GitHub 和 Gitee，两个平台均覆盖公开与私有仓库；这取代上一轮的单平台范围。
7. 首期只读导入远端工程；远端提交与推送不纳入当前范围，不影响导入副本的后续修改、开发与测试。
8. 私有仓库采用 A：用户手动填写个人访问令牌（Token）；首期不采用 B 的平台网页授权，不注册用于该授权流程的 OAuth App 或 GitHub App。
9. 提供 Token 获取辅助按钮，按 GitHub / Gitee 打开对应官方获取页面；用户自行创建并复制回导入表单，不自动生成或回填 Token。
10. Token 需要由后端加密保存，供后续导入复用；不采用仅本次导入使用的方案，用户可以删除已保存凭据。
11. Git 导入允许用户选择当前仓库所有有权限读取的远端分支，不限制为默认分支；“所有分支”不包括凭据无权访问的仓库或分支。
12. 分支选择交互参考 Codex 的 Git 分支选择，不采用只填写默认分支或硬编码主分支的入口。
13. 文件夹上传和 Git 仓库导入每次均创建独立新应用，不覆盖或合并平台已有应用；该边界同时适用于首期和后续，不规划导入覆盖旧应用的功能。重复导入同一来源或导入不同分支，也不得改写已有应用。
14. 不覆盖已有应用是导入行为的边界，不限制在导入完成的新应用内继续进行代码编辑、AI 增量改造、运行与测试；这些能力按小步骤独立设计与验收。
15. 导入完成后不自动运行项目；项目启动由用户主动触发，在隔离工作副本与沙箱中执行。导入成功不等于运行成功或通过业务验证。
16. 首次导入期间不安装依赖；导入完成后弹窗询问用户是否安装，只有用户选择安装后才执行。
17. 用户在导入后的弹窗选择否时，实际应用界面保留“安装依赖”按钮，允许后续主动触发安装。
18. 用户点击“运行”时，若当前项目缺少依赖，再次弹窗询问是否安装；不能静默安装或在缺少依赖时直接启动项目。
19. 用户已点击“运行”，并在缺依赖弹窗确认安装时，安装成功后自动继续本次运行；安装失败或用户取消则不启动。该行为只延续用户主动发起的运行，不适用于导入后的安装弹窗或独立“安装依赖”按钮。
20. 文件夹上传默认不跳过依赖目录或构建产物，包括 `node_modules`、`.venv`、`dist`、`target` 这类目录；不采用上一轮建议的默认排除方案。
21. 是否跳过这些目录由用户在设置中选择，默认关闭跳过；设置按用户作为长期偏好保存，具体过滤规则和界面位置后续设计。
22. 文件夹上传默认排除可能包含密钥的本地敏感配置，保留 `.env.example` 等配置示例；需要时允许用户明确选择包含敏感配置。此规则与依赖目录、构建产物默认保留的规则分开。
23. 导入过滤设置属于每个用户的长期偏好，后续导入沿用其已保存选择，用户之间相互隔离；修改偏好仅影响后续导入，不追溯删除或重写已导入应用的文件。
24. 允许用户手动选择运行目录；未手动选择时默认自动扫描工程，识别候选启动目录。手动选择优先，不被自动扫描结果覆盖；扫描只做识别，不安装依赖、不启动项目。
25. 用户主动发起运行后，启动服务前扫描并列出候选服务清单，由用户选择启动目标；不能随意采用第一个识别结果或默认启动全部候选。
26. 服务清单允许多选，例如同时选择前端和后端；启动范围以用户明确选择的目标为准，未选择的服务不启动。多服务运行的实际实现与验证按小步骤单独推进，不等于已支持或已验收。

28. 启动识别增加多层检查，提高对不同工程结构与启动方式的覆盖，减少要求用户手动补充信息的情况；后续第 43–44 条已确认层次与 Agent 触发范围，不将此要求解释为保证全部工程识别成功。

## 主流程与结果归属：建议实现

1. **准备来源**：选择文件夹或 Git；Git 选择平台、仓库、自己的凭据和一个分支。Token 获取页只辅助获取，不自动授权。
2. **隔离读取**：文件夹接入暂存区，Git 只读拉取至本次任务的暂存区；此时不安装依赖、不运行项目、不向远端写入。
3. **确认范围**：以长期偏好和本次选项形成待接入清单，展示文件数量/大小/排除项；Git 记录实际读取 commit。预览与实际读取版本不一致时不能混用旧摘要。
4. **提交新应用**：校验内容、路径与用户归属，形成新的独立应用和工作副本；导入任务完成后才显示可用应用。数据库与文件提交失败时不得留下假成功，补偿与清理须有可核对状态。
5. **导入后安装提示**：按已确认流程询问是否安装。用户拒绝保留按钮；单独安装不自动运行。
6. **用户运行**：读取当前版本的自动/手动配置，展示服务清单及已列明的必要构建；按已选目标检查依赖，必要时确认安装，再执行必要构建并启动这些目标。构建失败/取消则不启动对应服务，不能把构建成功当作运行或业务验收成功。
7. **独立记录结果**：安装、运行、服务故障、修复及验证分别记录；结果关联本次应用/任务/服务/代码版本，不把导入来源 commit 当作后续修改版本。

建议记录以下信息；这是逻辑职责，不要求一类信息就建一张新表或一个新服务：

- 导入任务：用户、来源类型、仓库/分支/实际 commit、过滤选项快照、凭据引用/版本、暂存范围、阶段/结果、脱敏错误和清理状态。
- 应用来源：新应用标识、导入任务、原始来源版本、初始内容清单；展示名称不是文件隔离或访问权限依据。
- 用户设置与凭据：长期过滤偏好、多份加密 Token 与备注/平台归属；令牌值不放入应用工程或运行证据。
- 运行配置：该应用的服务、工作目录、启动/依赖入口、来源依据和所对应的代码版本；自动候选与手动修正分开保留。
- 执行与证据：安装/运行/验证的任务标识、目标、环境、结果与独立证据路径。

实施时先核对现有实体、配置、工作区解析与事件通道的复用点，再确定字段、存储和接口；不凭这份草案擅自重写架构。

## 并发、取消与保护：工程默认建议

- 不同导入任务使用不同 staging 和应用标识；重复点击同一次确认不能形成同一任务的两次提交，明确发起的再次导入仍创建新应用。
- 同一应用的安装与启动按现有协调能力防冲突；旧版本候选或迟到事件不得覆盖新版本状态，具体协调机制在实现前结合源码确定。
- 取消/失败处理只清理当前任务拥有的未完成资源。文件提交、应用可用状态、取消和凭据更新相遇时，要用可验证的状态条件避免“已取消又成功”。
- 路径与命令校验只是入口检查；工程脚本本身也可能启动进程、读写文件和访问网络，必须依靠独立副本、真实沙箱、权限和资源边界保护原工程。
- 上传默认保留大目录，不意味着无限资源或静默截断。具体大小/数量/耗时及 CPU/内存/进程/磁盘/输出/网络限制由现有配置与样本评估确定，越限明示，不能偷偷改成默认跳过。
- 构建、测试或模型辅助不会由导入成功隐式触发；后续命令、权限、目标与预算在实际执行前说明。没有验证证据不宣称可部署，不自动发布生产。

## 分层启动识别：三层顺序已确认，具体算法待验证

工程补充见[启动识别与运行计划契约](./project-import-startup-plan-contract.md)：细化候选、扫描诊断、计划版本、准备授权、多服务故障与旧结果边界；均未实现，不把方案建议扩写为新增已批准交互。

目标是减少漏识别与误识别，不是承诺扫描结果一定可运行。增加目录深度只能改善文件发现；仓库未声明的参数、动态生成的入口或缺失配置，不能靠重复扫描凭空补齐。

用户在后续澄清中确认三层顺序及 Agent 授权条件。以下各层检查内容为工程建议，须逐层独立验证：

1. **固定扫描**：检查各框架的标准启动文件位置与显式运行声明，例如 `.glyahh/run.json`、标准工程配置与入口。发现文件只是线索，仍需核对目录、文件内容与命令来源；不靠存在 `pom.xml` 就认定 Spring Boot。此层不调用模型。
2. **算法识别**：固定扫描未识别时，以有界工程遍历、配置解析、工作区/子工程关系、框架与源码入口交叉核对补充识别。可分析 `package.json` 的 scripts、锁文件、Maven/Gradle/Python 声明、启动脚本、Dockerfile/Compose/Procfile；具体规则归属和实现由样本验证，不再把这些依据另列成第四层。此层不调用模型，也不运行工程脚本。
3. **Agent 识别**：第一、第二层都未识别时，先提示未识别范围与模型调用，再由用户决定是否使用 Agent；用户拒绝不调用模型，保留手动配置入口。批准后仅读取当前应用合法源码、配置及 README 等说明，提出候选服务、目录、启动命令与依据，区分事实、推断与未知，不读取密钥或执行建议命令。

识别授权不等于安装依赖或启动服务授权；候选仍回到服务选择清单。第一、第二层调用异常或扫描被限制时，应显式呈现失败/不完整，不能无声当成“没有识别”并触发 Agent。

第三层触发范围已确认按未识别部分计算，而非要求整个项目没有结果。提示需展示拟补充范围；相关上下文读取不等于重新替换全部服务配置。前后端中仅后端未识别时，保留前端候选并在批准后补充后端，最终仍由用户选择启动目标。

交叉核对与保护边界建议：

- 已确认的手选目录优先；扫描不能无声更改用户选择。显式运行声明也是待校验的工程数据，不因其存在而绕过服务选择、依赖安装确认或路径与权限限制。
- 只扫描对应应用的工作副本，限制目录深度、文件数量、读取大小和耗时；具体限额由样本评估。限制触发时标记“扫描不完整”，不能假装已经检查全部文件。
- 上传保留依赖和构建目录的规则不变；识别时不将依赖包、缓存、测试示例里的启动文件列为用户服务。工程明确声明的静态产物可作为该工程的入口依据，不把整个产物树当成多个独立服务。
- 相同服务的不同线索合并，互相矛盾的入口保留歧义；候选记录服务目录、命令来源、证据文件和当前应用/代码版本。依据不足不靠模型自评分冒充确定性结论。
- 分别记录“已发现候选”“待确认”“未识别”和真实运行结果；状态具体呈现在后续前端评审中核对，不再将已确认的识别顺序和授权条件列为未决。手动配置补充已经确认，不能用盲猜命令替代用户决定，也不能把手动输入的命令视为已验证可运行。

- 自动识别优先，并允许用户自行补充或修正服务名称、运行目录与启动命令；填写配置不自动安装依赖或启动服务。

## 多服务的部分失败与重试

- 本节处理的是服务启动阶段的单项失败；此前确认的安装失败或用户取消不启动规则仍适用，不因多选而绕过安装确认。
- 某项启动失败时保留已启动成功的其他服务，分别展示状态、错误与日志；整体显示“部分失败”，不能由一个进程存活推断全部服务或业务正常。
- 用户可以主动重试失败项；重试仅针对失败服务，不重新启动成功项，不影响其他应用或本次未选择的服务。
- 失败项的残留进程、端口等资源须在重试前核对与清理，不能把成功服务作为失败项资源清理；具体机制后续结合实际执行链路设计与验证。
- 后续独立验收覆盖部分失败时成功服务仍运行、失败项错误可回放、单独重试不会重复启动成功项，以及所有状态与日志属于正确应用、服务和代码版本。当前仅完成需求记录，没有实际多服务失败或重试验证结果。

- 默认保留依赖目录和构建产物；不得为了减少上传量，在用户未开启过滤设置时隐式剔除这些目录。
- 敏感配置默认排除，配置示例保留；用户明确选择包含时再接入。具体识别规则和确认交互后续设计，不默认排除全部工程配置。
- 设置提供用户可选的跳过规则，并按用户长期保存供后续导入复用；本次导入允许临时调整，不自动改写长期偏好。导入确认采用摘要与可展开详情已确认，具体过滤选项、调整入口及统计机制仍待设计。
- 未设置偏好时沿用已确认的初始默认值：依赖和构建目录不跳过，敏感配置默认排除，配置示例保留。用户修改后不应用到其他用户或已导入应用的文件。
- 目录被保留，不代表其中的依赖适用于实际沙箱环境；依赖就绪检测仍需执行，不能仅以目录存在替代验证，也不能据此静默重新安装。
- 默认不跳过不等于取消路径、权限或资源限制；这些强制校验与用户可选过滤须分开，具体限制后续以工程样本核对。
- 后续验收核对默认设置下依赖、构建目录及其文件实际被保留；用户启用跳过后只过滤选定范围，不改写原目录或已有应用。当前没有实际上传或设置验收结果。
- 敏感配置的独立验收覆盖默认排除、示例保留、用户明确包含，以及配置不串写其他应用。示例文件名不保证内容无密钥，识别能力的局限须如实标记。
- 用户允许包含敏感配置不等于允许将密钥送入模型上下文或输出到日志；后续设计须区分工程文件保存、沙箱使用与模型读取边界，不能因导入选择而省略保护。
- 长期偏好的独立验收覆盖重新登录后保留、后续导入沿用、不同用户隔离，以及修改偏好不更改已导入应用文件；当前未执行这些验证。
- 本次导入选项的独立验收覆盖默认沿用长期偏好、临时调整按本次选择生效、后续导入仍沿用原有偏好，以及临时调整不改写已导入应用或其他用户的数据；当前未执行这些验证。

- 摘要依据本次实际过滤选择生成；用户临时调整规则后须更新统计，不使用旧摘要代表新选择，也不因统计困难无声改变已确认的过滤规则。

- 后续独立验收分别覆盖两个入口的摘要与详情、过滤变更后的统计更新、排除项与实际接入文件一致，以及展示预览不安装或启动服务。当前未实现确认界面，也未执行这些功能测试。

## 依赖安装交互

以下流程已确认，但尚未实现或进行实际功能验证：

1. 导入工程，创建独立应用；此阶段不安装依赖、不启动项目。
2. 导入成功后直接进入该应用的 Agent 工作台（现有 `/app/:id/chat` 入口），不再停留在导入成功页；不携带 `autoSend` 或自动生成提示。工作台内弹窗询问是否安装依赖。
   - 选择安装：在该应用的隔离运行环境中执行依赖安装；仅安装，不因此自动启动应用。
   - 选择否：不安装，留在当前工作台并保留“安装依赖”按钮。
3. 用户随后可通过应用界面的“安装依赖”按钮主动安装。
4. 用户点击“运行”时先扫描并展示候选服务清单，由用户选择启动目标，再判断所选目标的依赖是否就绪；缺少依赖时再次弹窗，未获得安装确认前不安装、不启动。
5. 在第 4 步弹窗中确认安装后，安装成功就继续同一应用、所选目标的本次运行；安装失败或用户取消则不启动。导入后的安装确认与独立安装按钮只授权安装，不构成运行请求。

识别依赖是否就绪须结合工程类型、当前依赖清单与实际隔离运行环境设计，不能只因过去安装过一次就永久标记就绪。具体检测、状态失效与失败重试机制后续核对，不以模型判断代替验证。

后续独立验收至少覆盖：首次导入未安装未启动、弹窗拒绝后按钮仍可用、通过按钮安装不启动、缺依赖点击运行再次弹窗、确认安装成功后继续本次运行、取消或安装失败不启动，以及状态属于当前应用和代码版本。当前没有这些流程的验收结果。

## 导入与项目运行的边界

- 导入流程不得自动执行应用启动命令或通过后台任务隐式启动项目。
- 结构识别建议静态读取目录与工程配置，不将配置中识别到的启动命令立即执行；具体识别能力后续设计与验证。
- 界面与任务状态须区分导入完成、运行中、运行失败以及验证结果，不能用导入成功宣称项目能运行或可部署。
- 后续验收核对：导入完成后无应用启动进程、无自动启动任务；用户主动触发运行后，执行只影响对应新应用的隔离工作副本。
- 依赖安装由用户确认或按钮触发；仅用户已主动发起的运行请求可以在确认安装成功后继续。测试触发与授权已由测试验收专项收口；必要构建也已确认包含在用户所选运行方案的授权中，不再列为未决。目前没有实际执行验证结果。
- 构建只在对应应用的隔离副本与沙箱内执行，绑定所选服务、代码版本和任务；不在原工程或其他应用执行。出现新增依赖安装、额外权限或未声明执行步骤，不能用“构建”名称绕过确认。工程建议：构建命令及自带生命周期测试在启动方案中说明，不擅自额外运行平台验收，也不默默跳过命令已有测试来制造成功。
- 安装脚本自身必要的原生依赖编译与平台另外触发应用构建分开记录；前者仍受安装授权、脚本副作用检查和沙箱限制，不将“单独安装不自动构建运行”误解为所有依赖都能免编译安装。
- 多服务构建/启动逐项记录结果。一个服务构建失败时不启动该服务，不误停已有成功服务；重试遵守只重试失败项的既定规则。

## 导入来源、版本与应用隔离的验证边界

- 后续验收至少包含 GitHub 和 Gitee 的非默认分支导入，并核对最终文件来自所选分支。
- 每次导入只能选择一个分支，前后端均须保证单分支约束；不能因请求携带多个分支而隐式批量创建应用。不同分支的导入分别发起、分别核对来源和新应用。
- 分支会随提交变化，导入结果须记录来源仓库、所选分支和实际提交版本，后续任务与证据绑定该版本，不能只用分支名区分结果。
- 首期来源选择仅支持分支，不提供 Tag 或指定历史提交入口；实际导入 commit 必须与最终接入文件对应，不用预览时的旧信息冒充实际读取版本。后续修改的代码版本与导入来源版本分别记录，不宣称修改已同步远端。
- 重复导入同一工程以及导入同一仓库的不同分支时，核对产生不同的新应用标识和独立工作目录；既有应用的代码与业务状态保持不变。
- 新应用名称默认取文件夹名或仓库名，用户可以修改；名称不用于决定覆盖旧应用，也不能作为跨应用读写依据。名称校验与重名展示细节后续设计。
- 后续独立验收覆盖两个入口的默认命名、用户修改后名称正确保存、重复名称不导致覆盖，以及来源记录与应用标识不因修改名称而串写。当前未实现命名交互，也未执行这些验证。
- 导入失败不得修改已有应用；保留失败记录与脱敏错误信息，清理未完成副本，并允许用户重新发起导入已确认。任务状态、清理机制与重试交互后续设计。
- 当前只完成需求记录，未核对 Codex 的实际分支选择界面，也未验证分支列举或导入功能。

## 导入失败与重新导入

- 导入失败保留失败记录与脱敏错误信息，供用户查看原因并重新发起导入；不能将部分文件接入或临时副本存在当成导入成功。
- 清理仅针对当前失败导入任务拥有的未完成副本与临时资源，不触碰原工程、远端仓库、已有应用、已保存 Token 或失败证据记录；具体隔离与清理机制尚待设计。
- 用户重新发起的是新的导入任务，成功后形成新的独立应用；不得复用其他应用的文件或拿此前失败状态作为本次成功结果。重试如何复用用户输入、再次读取来源与确认范围，后续设计。
- 清理未成功时须如实记录，不能宣称已经清理或已经导入；失败与清理状态的具体交互后续设计。
- 此规则只针对导入阶段失败。应用已成功导入后，依赖安装或服务启动失败不得因此删除工程文件，仍按安装/运行的既有流程处理。
- 后续独立验收覆盖两个入口的失败记录与错误脱敏、未完成副本清理、失败结果不可误标为可用、重新导入成功，以及原工程和已有应用保持不变。当前未实现失败处理，也未执行清理或重试测试。

## 已保存凭据的安全边界

以下是后续实现和验收必须落实的边界，不代表当前已具备这些能力：

- 按当前魔方用户与 GitHub / Gitee 平台隔离；只能使用、替换或删除自己的凭据，不允许跨用户复用。
- 同一用户可以在同一平台保存多份 Token，各份凭据独立管理；新增、替换或删除某一份，不得误覆盖或删除其他凭据。
- 后端仅持久化密文；加密密钥与密文分开管理，密钥不提交到版本库。
- 前端展示配置状态，不提供完整 Token 回显；不将 Token 持久化到浏览器存储。
- Token 不进入模型上下文、导入后的源码、仓库地址、命令参数或日志；具体传递方式与泄露检查在实施前设计。
- Token 失效或权限不足时，提示用户重新填写或调整权限；手动 Token 方案不承诺自动续期。
- Token 替换后，后续导入使用新值；不能让旧值与新值在同一任务中静默混用。使用凭据版本并终止受影响旧任务、由新凭据重试是本草案的工程建议，不冒充用户已经明确选择了该在途策略。
- 删除平台保存的凭据后，不能再用于后续导入；远端撤销仍由用户在 GitHub / Gitee 管理页面完成。
- 删除 Token 同时取消依赖该凭据的未完成导入，范围按凭据与任务关联核对，不按用户名批量取消全部任务。已完成应用及其他凭据/任务保持不变；取消与一般导入失败分别记录。
- 已取消任务的晚到响应或事件不得将其改写为成功；本任务未完成副本与资源按隔离边界处理，不删除已完成工程或证据记录。具体取消、状态协调与清理机制尚待设计，当前没有实际任务取消验证。
- 后续独立验收覆盖同一用户/同一平台保存多份、新增不覆盖、单份删除不影响其他凭据、跨用户访问被拒绝，以及前端、日志和模型上下文不泄露完整 Token；当前未执行这些功能验证。
- 删除凭据的独立验收覆盖相关未完成任务取消、未来导入不能继续引用、晚到结果不能恢复成功，以及已完成应用和其他任务不受影响；当前未执行这些验证。
