## 1. 产品约束不变

- 导入后不自动安装、构建或运行；安装弹窗由用户决定，拒绝后应用内保留安装按钮。
- 固定扫描、算法识别、授权后的 Agent 识别按三层推进。前两层均未识别的部分可请求 Agent 补充，不要求全仓零结果；拒绝后可手动输入。
- 手选目录和手动配置优先，按应用保存；运行前重新校验。不能因为扫描完成就执行候选命令。
- 启动前列出服务，由用户选一个或多个；只启动选中目标。点击运行包含所选方案中已列明的必要构建，缺依赖仍须确认安装。
- 一项启动失败保留成功项，整体显示部分失败，重试只针对失败项。导入文件不因安装/运行失败被删除。
- 流程沿用原工作台，不新增独立聊天、强制模式切换或自动生产部署。

以下字段、状态、调度和兼容方式是研发建议，不冒充用户已批准的全部工程细节。

## 4. 三层识别：先发现范围，再识别入口

扫描基于一致的只读输入。先短暂协调受管写入建立清单/副本，再释放工作区，不让长扫描锁住用户编辑。后续修改使候选过期，不能把混合读取的新旧文件称为同一快照。

1. **发现范围**：有界遍历目录和工程成员声明，记录手选目录及相邻配置关系。发现子目录不等于已经识别其启动方式，不新增第四个识别层。
2. **固定扫描**：对发现的工程范围按标准位置与明确声明识别候选；检查配置内容和入口存在性，不凭文件名执行固定命令。
3. **算法识别**：对未识别范围解析配置、模块关系和源码入口；已有候选保留。多个合理入口没有足够依据时保留歧义，不机械取第一个。
4. **Agent 补充**：仅对前两层确实未识别的范围申请用户同意；允许读取相关合法上下文。使用同一 Agent 能力的只读工具边界，禁止 Shell/写文件/安装/运行及凭据读取；输出结构化候选，仍经过服务端校验与用户选择。

每层分别记录 `IDENTIFIED / UNIDENTIFIED / AMBIGUOUS / INCOMPLETE / FAILED`。全仓可以同时存在已识别和未识别范围；没有入口的库项目也可以有“不是可启动服务”的诊断。

- 扫描超限、读取失败、声明损坏不是“前两层未识别”；先显示具体失败/不完整范围，不自动转 Agent 兜底或发布假完整结果。
- 歧义不是简单未识别；先展示冲突证据与手动修正入口。若需要改变已确认的 Agent 触发范围，另行对齐，本文不擅自扩大。
- 排除依赖、缓存、报告、历史快照与测试样例作为服务候选，不删除这些导入文件。明确声明的静态产物按所属工程处理，不遍历成许多服务。
- 不跟随越界符号链接；配置解析不执行 Maven、Gradle、Python import、包管理器、Compose 或仓库脚本。安全解析器禁用外部实体/文件加载，并限制输入规模；具体库以现有依赖和样本评估为准。
- README/配置/Agent 返回内容都是工程数据，不能改变授权或读取保护。敏感文件接入不等于授权送模型，模型不可读取历史错误分支与保护快照。

## 5. 配置依据与成熟方案复用

| 工程 | 静态识别建议 | 不能据此宣称 |
| --- | --- | --- |
| Node/Web | 解析 scripts、packageManager/锁文件和 workspace 成员，核对入口及对应运行器；多个锁文件冲突明确呈现 | 包管理器已安装、依赖可用、任意脚本是服务、已有 dist 是最新 |

| 静态/其他 | 验证明确静态入口和相对资源；读取 Docker/Compose/Procfile 仅作线索 | 自动执行 Compose、挂载 Docker socket、任意镜像/外部服务已获批准 |

优先借鉴开源检测规则并复用现有解析库，不将完整构建平台直接塞进 Java 服务：本轮核对 [Railpack Node provider](https://github.com/railwayapp/railpack/blob/main/core/providers/node/node.go)，其启动识别读取 scripts、入口与框架线索，也可能没有命令；其包管理器兜底、依赖裁剪等产品策略不自动复制到本项目。未安装或运行 Railpack，复用代码仍须固定版本、许可与样本验证。

npm 的 pre/post 生命周期会伴随脚本执行，安装也可能执行 prepare；不能只展示一条表面命令并宣称没有其他工程代码执行。需按工具版本记录可静态确认的生命周期和未知部分，权限由实际沙箱限制，而非字符串保证。[npm Scripts](https://docs.npmjs.com/cli/v11/using-npm/scripts/)

Maven 多模块构建已有 reactor 和模块依赖排序，优先使用项目既有构建机制，不另造平台级 Java 构建器；构建其他依赖模块不等于启动其他服务，但其范围必须列入计划。[Maven 多模块指南](https://maven.apache.org/guides/mini/guide-multiple-modules.html)

## 6. 候选变成运行计划，不直接执行

1. 用户手选目录只约束本次目标发现/工作目录，不丢弃其他已导入文件；已知依赖根可在应用内部不同目录，不能越出工作副本。
2. 展示候选服务、识别来源和必要缺项；支持手动修正。研发建议初次不自动选中全部或第一项，展示推荐而由用户决定；最终默认选择规则留前端评审，不冒充新增已批准交互。
3. 选定服务后生成不可变 planRevision：列明依赖检查与安装范围、必要构建、启动命令、工作目录、环境需求、就绪方法和共享步骤。危险/未知权限不因用户选中服务就获授权。
4. 本次运行授权绑定该计划。批准 Agent 识别、保存手动配置、曾经运行成功，均不替代本次运行与缺依赖安装确认。
5. 路径、真实入口、配置版本、输入内容与资格在启动前再次核对；计划或权限实质变化就失效原授权，呈现差异，不偷偷换命令继续。

选中 A 服务但其脚本启动 A+B 的情况必须识别为可能扩大服务范围。明确的聚合脚本要展开为服务选择或经用户重新确认，不当作“只启动 A”。静态无法证明实际子进程行为时记录未知，并以执行资源登记/运行边界核验，不能声称命令校验可证明脚本全部副作用。

## 7. 安装、构建和运行的授权分离

- 依赖检查只有 `READY / MISSING / INCOMPATIBLE / UNKNOWN` 等证据状态；目录存在、旧成功标记、锁文件相同不单独证明就绪。检查工程代码若需执行，则属于受管检查步骤，不在只读扫描时隐式执行。
- 导入后确认安装或独立按钮只执行已说明的依赖准备及固有生命周期，不接着启动服务；用户已经发起运行且确认缺依赖安装时，成功后继续同一有效计划。
- 编译/构建本身需要下载依赖时，同样纳入依赖准备确认；不能把 mvn package 等名称当成免安装授权。工具可能运行中才发现缺项，未获准备权限则停止并明确提示，不静默继续联网补齐。
- 安装成功凭据绑定依赖清单、平台环境、工具和实际检查；Node 开发依赖、Python 原生扩展、Java 模块依赖按所选方案核对。带入依赖不可用不默默重装，重新征得安装同意。
- 共享安装/构建步骤可按同一计划和输入只执行一次，列明影响的已选服务与工程模块；失败只阻塞依赖它的服务。不能用相同命令字符串跨应用或跨环境复用成功。
- 安装/构建的预期产物写入隔离执行副本，记录输入、执行后变化和产物身份；生成输出不作为用户修改偷偷合回主工作区。若修改启动脚本、依赖声明或其他计划依据，需要校验变更后的执行方案，不能继续套用旧批准。
- 不额外触发平台验收、不生产部署，也不默默增加 skipTests/忽略错误参数来制造成功。原脚本固有测试记录为原步骤效果，不当平台全面验收。

## 8. 运行状态与多服务故障

2026-10-06 健康路径实现契约增量（第一项内部，不新增界面）：`.glyahh/run.json` 的每个 `processes` 项可声明 `healthPath`，必须同时声明合法 `port`。路径限定为以单个 `/` 开头的 URI 路径，长度最多 512，不允许来源、查询、片段、反斜杠、控制字符或 `..` 路径归一化变化；错误声明明确失败，不忽略后改查根路径。未声明路径时原默认 `/` 保留。

路径从只读声明进入候选，再进入已确认计划的 `readiness.path` 与 planRevision；执行只能使用冻结的服务身份、目录、命令、端口和路径。检测向容器对应的 `127.0.0.1` 映射端口发送 GET，只接受 2xx，不跟随重定向、不携带身份凭据；原运行地址仍保留根地址，不将健康地址冒充项目首页。根路径 404 不影响明确健康路径 2xx 的启动判据；健康判据通过不代表业务全面验收。

识别规则升级为 `import-startup-2026-10-06-v3`，已有旧规则识别/计划需要重新扫描和确认，不套用忽略过健康声明的旧授权。持久 JSON 可保存新字段，无数据库迁移。

扫描状态与运行状态分开。建议本次运行链路：

```text
PLAN_READY -> VALIDATING -> CHECKING_DEPENDENCIES
  -> WAITING_INSTALL_APPROVAL -> INSTALLING -> VERIFYING_PREPARATION
  -> BUILDING -> STARTING -> CHECKING_READINESS -> READY
```

依赖已就绪跳过安装，无必要构建跳过构建，是计划本身不需要该步骤，不是失败后降级。用户拒绝或取消本次安装时不继续本次待执行运行，不借其他服务无需安装而绕过取消；安装失败不启动需要该准备的服务。既有成功运行项不因新的安装拒绝而误停；每个服务维护自己的阶段，不能全组只有一个绿色状态。

- 任一执行阶段可进入 `FAILED`；取消进入 `CANCELLING`，确认实际停止后才是 `CANCELLED`，停止失败为 `STOP_FAILED`。失败状态不证明后台进程已停止。
- 聚合状态区分全部就绪、部分失败、无服务就绪、取消中和停止失败；“就绪”只说明选中服务通过其启动判据，不证明业务或整个项目验收。
- 有网络服务记录实际地址/端口与进程归属；无网络 worker 保留存活/业务特定就绪依据，不强行生成 HTTP URL/QPS。库和一次性任务不冒充常驻服务。
- 成功项按原计划保持运行；失败项重试前确认残留与版本。工作区已变化时不能偷偷把新版失败项与旧版成功项拼成“同一版本成功”，须呈现版本差异并重新确认计划。
- 实现应允许独立控制服务失败域。可评估复用 RuntimeManager 按服务运行单元管理容器/进程，避免默认一组 wait -n 导致全停；共享资源、端口与调用关系须单独验证，本文不强制每服务容器或新增编排平台。
- 正常运行后台进程也可能写文件；执行副本、资源登记和共同写入闸门须覆盖它们。回档/权限撤销须停止相关资源，不允许旧进程在恢复后继续写入或用旧就绪事件污染新状态。

## 9. 失败、重启与迟到结果

| 时点 | 必须处理 |
| --- | --- |
| 扫描中源码变化/超限/异常 | 保留诊断，候选标过期/不完整；不得自动改为未识别并调用模型 |
| Agent 返回时任务或 epoch 已撤销 | 不提交到当前候选/计划，不自动启动；合法历史证据与模型可读资格分开 |
| 用户确认期间修改配置 | 用 plan/config revision 比较拒绝旧确认，展示实际差异 |
| 安装/构建中断 | 保留错误、执行资源与产物清单；不把残留当 READY，重试不重复运行成功服务 |
| 平台重启 | 核对任务与实际容器/进程身份，不仅凭 DB RUNNING；没有有效授权不自动重启服务 |
| 取消/停止失败 | 显示未停止资源并阻止相关恢复/重用；不误杀其他服务或应用 |
| 新工作区收到旧结果 | 校验 app/task/run/plan/snapshot/epoch/seq；旧结果不覆盖当前状态 |

重启恢复采用日志/状态记录与真实资源对账，不自动重跑会产生副作用的安装、构建和脚本。清理执行残留不删除已经成功导入的工程，也不将旧日志、旧计划和保护快照重新喂给当前 Agent。
