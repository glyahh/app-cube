> 类型：技术调研；候选方案与资料核对不代表已实施。 当前事实以[项目状态](../status/current.md)及对应版本源码、验收证据为准。

## 1. 必须分清的四种东西

1. **验收标准**：定义应该满足什么，不是测试程序。
2. **执行工具**：执行断言、请求或负载并产生结果，不知道所有真实业务预期。
3. **已知答案的基准项目**：衡量平台/Agent 能否找到已知问题，不是任意用户项目的生产认证。
4. **用户项目测试模板**：把标准、执行器、参数和独立业务预期组合成可复用规则，仍需适用性判断。

不能把一个安全基准、Agent 解题排行榜或开源仓库 star 数当成“官方验证整个项目企业级”的证据。以下建议是结合本项目约束作出的设计推论，而不是来源对本平台的背书。

## 2. 标准与基准候选

### OWASP ASVS

官方仓库定义 Web 应用与服务的安全验证要求，要求引用时附带标准版本以免编号变化；可作为权限、输入、安全配置等测试规则的来源。采用固定版本条目与原始标识，不能直接把它当“所有程序企业级清单”，也不能凭模型说满足就算达标。[官方仓库](https://github.com/OWASP/ASVS)

资料页面提供 5.0.0 的稳定版本入口，并注明项目内容为 CC-BY-SA-4.0；实际选用版本和许可义务应在模板引入时登记。暂不将标准全文复制到产品文案。[版本与许可说明](https://github.com/OWASP/ASVS#latest-stable-version---500)

### OWASP BenchmarkJava

它是带有故意设计的漏洞、用于评估漏洞检测工具的可运行 Java 项目。适合做平台安全检测能力的受控正负样本，不是正常业务 Demo，也不应直接用作用户验收模板。官方仓库包含预期结果和评分资源。[官方仓库](https://github.com/OWASP-Benchmark/BenchmarkJava)

官方页面将其定位为检测速度/准确性基准；项目页面列出 GPL-2.0。需隔离运行、固定 commit、独立保留期望答案，并在实际集成方式确定时核对许可，不自动暴露其服务或向用户工程植入漏洞。[项目说明](https://owasp.org/projects/benchmark)

### SWE-bench

基于真实仓库问题评估模型修复任务，适合借鉴固定问题实例、版本与独立测试的评测组织；不直接用于证明某用户应用可上线。测试 Agent 的发现质量和开发 Agent 的修复质量也应分别测，不混成一个自评分。[官方仓库](https://github.com/SWE-bench/SWE-bench)、[官方项目](https://www.swebench.com/)

本轮不引用排行榜成绩、不购买云执行服务、不跑整个评测集。后续若引入实例，需登记代码/数据集版本、资源要求和样本许可。真实用户项目验收依然依赖自己的业务断言和环境。

## 3. 执行与结果格式候选

| 候选 | 官方能力与本项目复用建议 | 必须验证的边界 |
| --- | --- | --- |
| Maven Surefire / JUnit | Maven test 阶段执行单元测试，生成 XML/文本结果；Java 项目先复用已有测试与结构化报告。[官方说明](https://maven.apache.org/surefire/maven-surefire-plugin/) | 集成测试与多模块命令不能仅按 Surefire 名称猜测；零用例、跳过测试和缺报告不能 PASS |
| pytest | 支持 JUnit XML 输出；Python 项目优先复用原测试与配置。[官方输出文档](https://docs.pytest.org/en/stable/how-to/output.html#creating-junitxml-format-files) | 插件/配置会影响收集与退出状态；统一核验跳过、失败、错误及实际收集数 |
| Vitest | 支持结构化 reporter；前端项目复用已有框架，适配实际锁定版本。[官方 reporter](https://vitest.dev/guide/reporters.html) | 本项目装的是 3.x 范围，当前在线文档不能证明与本地依赖完全兼容；待版本验证 |
| Playwright | 提供 JSON/JUnit 等 reporter，可采集端到端结果；优先用于浏览器实际行为与最终状态。[官方 reporter](https://playwright.dev/docs/test-reporters) | 浏览器/驱动/服务环境需就绪；截图或页面加载不代表业务正确，输出路径须限本轮 |
| Schemathesis | 基于 OpenAPI/GraphQL 生成输入与串联操作，可补接口边界、契约和状态序列测试。[官方仓库](https://github.com/schemathesis/schemathesis) | 接口契约可能不准确，业务不变量仍需独立预期；只能测授权的隔离端点，不能自动扩到所有路由 |
| k6 | 明确负载阈值与失败退出状态；用于用户选择的性能项，不作为整体核心定位。[官方 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) | QPS/延迟取决于业务与资源；必须记录负载模型、错误率、数据初态、预热和样本，不拿环境不足判产品失败 |

JUnit XML 不是单一完全统一格式，各框架版本存在差异；建议按框架生成可靠适配器，再落统一 `CaseResult`。用 schema 校验与固定正负样本验证，保留原始产物，不造一个大正则从自然语言里猜通过。

平台不默认给用户项目安装所有框架或新增业务依赖。仅在已批准测试方案需要且用户确认的隔离环境准备工具，保持原项目不变。已有测试优先，新工具必须证明必要性。

## 4. 执行隔离与资源保护

Docker 官方资料提供挂载、运行参数、CPU/内存等资源控制；这些是执行基础能力，不等于已经具备文件保护、后台取消确认、无网络副作用或一致性快照。[容器运行说明](https://docs.docker.com/engine/containers/run/)、[资源控制说明](https://docs.docker.com/engine/containers/resource_constraints/)

本项目当前 Docker backend 读写挂载开发 workspace、按 session 复用容器；宿主 worker 停止不证明容器内进程停止。因此要单独登记 testRun 资源与核验终态，不能直接套现有 Docker 类就承诺后台测试隔离。

## 5. 建议采用顺序，不是一次全部接入

1. 锁定一个带真实失败的内部业务样本，用其已有框架打通结果归一；报告和执行隔离优先于大量工具。
2. 对声明的 Java/Python/前端环境补齐已有框架适配；有 Web 流程才引入 Playwright，有接口契约才考虑 Schemathesis。
3. 整理固定版本的基准模板，用用户业务问卷补独立预期。再用已知答案样本检验 Agent 生成测试质量。
4. 性能、故障、供应链等按实际风险扩展，不默认装完一套工具箱。每个新增工具单独检查依赖、许可证、输出兼容、资源与取消行为。

这些工具不要求平台额外实现 OAuth 或购买测试 SaaS；模型调用、容器计算和存储仍有运行成本，不能把开源等同免费运行。具体采用的镜像/规则包是否有附加服务或许可限制须逐个核实，不能提前保证无第三方成本。

## 6. 后续每个候选必须补的验证记录

- 工具版本/commit、来源、许可证文件、镜像 digest 与依赖锁。
- 支持的语言/框架/操作系统、启动命令和所需环境；未知项明确标记。
- 通过、失败、零用例、跳过、损坏报告、退出码矛盾、超时/取消的原始样本。
- 测试输入与独立预期、最终业务状态、生成测试的正负识别质量。
- 原项目内容不变、容器/卷无串用、脱敏、安全解析、资源停止与证据回放。
- 若使用开源基准，固定数据和预期答案，不把答案喂给被测 Agent，不宣称基准成绩代表用户项目可上线。

本轮仅确认官方资料中的能力与定位。任何安装成功、适配通过、性能数字、漏洞发现率或企业级验收结论均待真实验证。
