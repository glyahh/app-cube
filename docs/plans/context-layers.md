# 上下文压缩分层策略

> 类型：设计与实施方案；目标架构、阶段状态不等于当前交付结论。 当前事实以[项目状态](../status/current.md)及对应版本源码、验收证据为准。

> 目标：给 V4 会话记忆加一套上下文压缩机制。
> 组合来源：**Hermes 的分层 + Claude Code 的预生成摘要 + 用户手动触发**。
> 本文档只讲设计，不含实现。
>
> 每个数字后面标了「抄自哪里」——没标的都是**待定**，需要按你自己的实测定。

---

## 一句话

**桌子满了怎么办？四道闸门，从最便宜的做起；只有前三道都不够，才花钱请人抄一遍。**

---

## 先分清：哪些是「层」，哪些不是

这是最容易混的地方，先说清楚，后面才不会有歧义。

| | 是什么 | 会不会自己触发 |
|---|---|---|
| **第 0 层** 结构性排除 | 一层 | 会（工具返回时） |
| **第 1 层** 确定性清理 | 一层 | 会（压缩时） |
| **第 2 层** 轻量裁剪 | 一层 | 会（压缩时） |
| **第 3 层** 摘要 | 一层 | 会（超阈值时） |
| 预生成摘要 | **不是层**，是第 3 层的优化 | **不会** |
| 手动压缩 | **不是层**，是第 3 层的入口 | **不会** |

**为什么要把后两个单列？** 因为它们不改变任何机制——预生成只是把第 3 层的计算**提前做**，手动只是给第 3 层**加一个人工开关**。它们都不新增一条规则，所以不算层。混在一起数，你会设计出四层会重叠、互相打架的东西。

**一共四层，加两个附属。**

## 比喻版（先看这个）

模型面前有一张桌子，桌上的纸能摊多少是**硬的**。每问它一次，它都要把桌上所有的纸**从头读一遍**——纸越多，每一轮越贵。

### 第 0 层：门口的保安

新纸要搬上桌之前，**先在门口量一下**。

太长的纸，只留头尾；再长的，干脆收进后面的抽屉，桌上只放一张小纸条写着「这张在几号抽屉里」。

**保安只管往里搬的东西。已经摊在桌上的纸，他一根手指都不碰。**

### 第 1 层：把废纸叠小（不花钱）

桌上那些已经用过、不会再看的草稿纸，**折成一行小字**。一模一样的纸，留一张就够。旧图片收起来，桌上只留最新的三张。

**这一层不动正文。你写的话、我写的话，一个字都不改。**

### 第 2 层：把更旧的草稿纸扔掉（还是不花钱）

桌角**最近放的那一摞不许动**。比这更早的草稿纸，全部扔进碎纸机，原地留个记号「这里原来有东西」。

**但要够量才值得开碎纸机。不够，一张都别扔。**

### 第 3 层：请人抄一遍（唯一花钱的）

前三道都做完了桌子还是满，才请一个人把**最早的那几摞**念一遍、写一张纸条夹在最上面。最近写的几页原样留着。**第一页永远留着**（那是你最开始说的话）。

**前面能解决，就不许叫他。他一次很贵。**

### 预生成摘要：趁早、趁别人不等的时候先把纸条抄好

**注意第 3 层和第 3 层以前的区别：第 0、1、2 层不花时间，第 3 层要花时间。**

真正请人抄一遍，他得把最早那几摞从头读到尾。实测一次要 **75 到 103 秒**。而这时候桌子最满，也就是你**最需要赶紧继续干活**的时候——你却要干等一分半。

所以换个做法：**不等桌子满，趁还没事的时候，先让人把「到目前为止」抄一张草稿纸条放进抽屉。** 真要用的时候直接拿出来。

**但草稿纸条有保质期——它只写到抄的那一刻。** 抄完之后你干的事，它不知道。

所以真用的时候，必须把「抄完之后到现在」那一小截**补上去**。不补，你会稳定丢掉最后那一段活，而且**纸条看起来是完整的**，只是少了一截，没人会告诉你。

**还有一条：草稿纸条必须自己带着「我算到哪了」和「我抄成功了没」这两个记号。**

因为它是**在后台抄的，抄砸了你不会知道**。前台用的时候如果不检查这两个记号，就会把一张抄砸了的纸条当成好的用——那丢的可就不是「最后一小截」，是「中间一整段」。这条后面单独讲。

### 手动压缩：自己按的按钮

不用等桌子满，你自己按一下就能让它抄。好处是**你可以在任务换挡的时候按**（这时候最省），而不是等到写满。

按下去之后：**抽屉里正好有新鲜的草稿纸条，就用现成的（几秒钟搞定）；没有或者太旧了，就现场算（等一分半）。**

**按按钮走的还是第 3 层那一套，不是新机制。**

## 四道闸门的硬边界

| | 什么时候动 | 动什么 | **绝不做什么** |
|---|---|---|---|
| **第 0 层**<br>结构性排除 | 工具返回、**进历史之前** | 按预算截断；超阈值的写盘并留引用 | **绝不动已经在上下文里的任何东西** |
| **第 1 层**<br>确定性清理 | 压缩时（和第 3 层同一时刻，**先于它**） | 去重；旧工具结果降级成一行；参数截断；旧图片降级 | **绝不调 LLM**；**绝不改对话正文** |
| **第 2 层**<br>轻量裁剪 | 压缩时，**在第 1 层之后** | 擦掉保护窗口之外的工具输出，替换成占位符 | **绝不调 LLM**；**绝不碰对话消息**；**不够门槛绝不提交** |
| **第 3 层**<br>摘要 | 占用 ≥ 阈值 | 切 head/summary/tail；写结构化摘要 | **前面能解决就不许调**；**绝不切开 tool 调用/结果对**；**绝不动最新一条用户消息** |

## 三条铁律

违反任何一条，这套东西就会开始互相打架。

### 铁律一：不许越层

**第 1 层能解决，就不许用第 2 层。第 2 层能解决，就不许用第 3 层。**

理由很实在：第 1、2 层是零成本的，第 3 层要花一次完整的大请求。如果第 1 层已经能把占用降回阈值以下，你调第 3 层就是白花钱，而且还白丢一次信息。

### 铁律二：不许倒序

**先叠小（第 1 层），再扔掉（第 2 层）。不能反过来。**

理由：第 1 层是「降级」——内容还在，只是变短；第 2 层是「擦除」——内容换成占位符，看不到了。如果先擦后降，你会发现本来能靠降级保住的东西已经被擦掉了。

### 铁律三：不许碰不该碰的

每一层都有自己的「不碰清单」（见上表最后一列）。**这套设计里最贵的错误不是「丢信息」，是「丢了我不知道」**——Claude Code #67500 里最伤的一条，是带着 `[未经验证的假设]` 标记的猜测被压缩后变成了语气确定的事实，标记消失了，模型开始拿它当定论用。

所以：**任何会丢内容的层，都要在丢掉的地方留一个「这里原来有东西」的痕迹**，而不是静默抹掉。

## 三个判定流程（照着走，不会有歧义）

### 流程一：工具返回时（第 0 层）

```
工具返回了
  └─ 超过单条预算？
       ├─ 是 → 截断；超过外置阈值就写盘 + 留引用
       └─ 否 → 原样入历史
```

### 流程二：到了该压缩的时刻（第 1 → 2 → 3 层）

```
占用 ≥ 前台触发点？（自动）/ 用户按了按钮？（手动）
  ├─ 第 1 层：去重、降级旧工具结果、截参数、收旧图
  ├─ 还是超阈值？
  │    ├─ 否 → 停在这里，不调 LLM ✓
  │    └─ 是 → 继续
  ├─ 第 2 层：算一下「保护窗口之外有多少能擦」
  │    ├─ 不够门槛 → 跳过（不提交）
  │    └─ 够 → 擦掉，替换成占位符
  ├─ 还是超阈值？
  │    ├─ 否 → 停在这里，不调 LLM ✓
  │    └─ 是 → 继续
  └─ 第 3 层：切段 + 写摘要
       ├─ 抽屉里有素材？
       │    ├─ 有，且标记完整、成功、不算太旧 → 当骨架用，从「算到哪条」往后补保留段（几秒）
       │    ├─ 有，但太旧（落后超过窗口 20%） → 放弃，现场算
       │    └─ 有，但标记缺失／状态是失败或空 → 放弃，现场算   ← 这条不能省
       └─ 没有 → 现场算（等 75~103 秒）
```

### 流程三：后台跑的时候（预生成）

```
占用 ≥ 后台触发点？且距上次更新够久？
  ├─ 否 → 什么都不做
  └─ 是 → fork 主会话发一个请求，整理「会话记忆」
       ├─ 成功 → 写回素材 + 标记「算到哪条 + 成功」
       ├─ 返回空 / 失败 → 写回标记「失败」，并触发熔断计数     ← 不能静默丢弃
       └─ 连续失败 N 次 → 熔断，停止后台任务，等恢复窗口到了再放一次探针
```

**三个流程里每一步「？」都是真检查，不是走过场。** 尤其是那两个「还是超阈值？」——检查方式必须是**供应商返回的真实 prompt token 数**，不是「消息条数变少了没有」。Hermes 专门强调过这一点，因为条数少但 token 没降太常见了（摘要本身可能很大）。

## 附属一：预生成 / 后台异步

### 它省的不是钱，是时间

第 3 层贵在两处：**钱**（输入是被压缩的全部历史，最贵的那次发生在最满的时候）和**时间**（实测 75~103 秒的停顿，而且卡在用户最想继续干活的那一刻）。

后台异步**只解决时间这一样**。钱还是照花。设计时的预期别定错。

### 关键纠正：后台做的是「素材」，不是「成品」

**这个必须一开始就定对，不然整个设计会错。**

一个自然的想法是「后台提前把前 N 条压好」。**这个想法是错的**，因为：

**后台跑的时候，你还不知道将来的切点在哪。** 后台按「前 30%」压了，将来触发时可能只需要「前 20%」——那你多压了 10%，白丢一段信息。反过来压少了又得补。而且会话在往前走，后台跑完那一刻的「前 30%」，过二十分钟已经不是同一个 30% 了。

**切点必须等到触发那一刻才能定**，因为那时候才知道要保留最近多长一段。

所以分开：

| | 什么时候做 | 产出什么 |
|---|---|---|
| **后台** | 占用到后台触发点，且距上次更新够久 | 一份**持续更新的会话记忆** + 一个**「我算到哪条」的标记** |
| **前台** | 触发压缩时 | 拿素材当**骨架** + 从标记处往后**补保留段** = 最终摘要 |

**后台省的是「读旧内容」那部分。切段和组装仍然在触发时做。** 这也是为什么它省的不是全部。

### 两个触发点必须拉开，而且是两套独立配置

后台一次要跑几十秒到一分半。**如果后台触发点和前台触发点一样，后台还没跑完前台就卡住了。**

| | 建议值 | 说明 |
|---|---|---|
| **后台**开始更新 | 约 50–55% | 要留出跑完的余量 |
| **后台**更新频率 | 每涨 10%，或每 N 次工具调用 | Claude Code 用三个条件：`minimumMessageTokensToInit` / `minimumTokensBetweenUpdate` / `toolCallsBetweenUpdates`（**常量名核到了，值没拿到**） |
| **前台**触发压缩 | 75% | 拿现成的用 |

**这两个必须是两套独立的配置，不能共用一个。** 共用的话后台永远来不及。

### 后台那个请求要 fork 主会话，别另起一个

后台跑的时候会发一个请求。**如果它另起一个请求、用了不同的模型或凭证，会把主会话的缓存挤掉。**

Hermes 对这条有明确态度，写成了规则——大意是：任何在对话中途静默换模型或换凭证的动作，都会让下一次请求 0 命中，所以**不要加会这么做的功能**。

反过来，如果**复用主会话的前缀**（Claude Code 的做法就是 fork 主会话：同样的 system prompt、同样的工具、同样的历史，只在最后追加一条指令），那它自己便宜，也不挤掉主会话的缓存。

所以：**后台请求 = fork 主会话 + 追加一条「整理会话记忆」的指令。**

> **待核验**：这条的细节（fork 时是否故意不设 `maxOutputTokens`、以及「不 fork 就 98% cache miss」那个数字）我列进了待核验清单，结论回来补。

### 失败兜底：素材必须自带两个标记，前台不信没有标记的素材

**这是整节最重要的一条，不能省。**

后台是异步的，**它抄砸了你不会知道**。如果前台拿到一张抄砸的纸条当成好的用，丢的不是「最后一小截」，是「中间一整段」。

参考一个真实的失败形态：OpenCode #44080 —— 推理模型只产出 reasoning 部件、没有文本部件，**系统照样把空壳标成 `summary:true` 落库了，不报错**。用户看到的是「整理完成」，实际什么都没存进去。

所以写死这条规则：

```
后台写回素材时，必须同时写入两个字段：
  - computed_through   → 我算到哪一条了
  - status             → success / failed / empty

前台取素材时：
  ├─ 缺 computed_through          → 不许当骨架用，现场算
  ├─ status 不是 success          → 不许当骨架用，现场算
  ├─ 有标记但落后超过窗口 20%      → 不许当骨架用，现场算（太旧了，补的段会很长）
  └─ 标记完整、成功、不旧          → 当骨架用，从 computed_through 往后补保留段
```

**这条规则的价值是：后台可以随便失败，前台永远不会因此丢东西。** 失败只是退化成「现场算」——也就是现在同步版本的行为，不是灾难。

**注意这不是「提醒用户」能替代的。** 提醒解决的是「用户不知道压缩在发生」，这条解决的是「前台的代码得知道压缩失败了」。两个不同的问题，两个都要做，但只有这条是硬性的。

### 竞态：四个必须写死规则的时刻

后台在算的时候，会话在往前走。这几个时刻一定会遇到：

| 时刻 | 处理 |
|---|---|
| **后台跑完了，前台已经在压缩了** | 素材写回但不用，下次再用。压缩以已经开始的那次为准，不打断 |
| **两次后台任务重叠了** | 加一个「正在跑」的标记，第二次直接跳过。不然两份素材会互相覆盖 |
| **后台跑到一半，进程重启了** | 「正在跑」的标记要有超时。启动时看到超时的标记就当没跑过，重新来 |
| **后台正在跑，用户按了手动压缩** | 不等它。手里有能用的素材就用，没有就现场算 |

> **待核验**：Hermes 有 `durable compression lock` / `watermark` 这套东西（用来保证压缩期间并发写入的尾部消息不丢），但我没拿到实现细节。这条我列进待核验清单了，结论回来补。

### 设置项

| 设置项 | 默认 | 关掉之后的行为 |
|---|---|---|
| 后台异步整理 | **开** | **退回同步压缩**（不是关掉压缩） |
| 后台开始更新的位置 | 约 55% | 不适用 |
| 前台触发压缩的位置 | 75% | 仍然生效 |
| 素材太旧就放弃的阈值 | 落后超过窗口 20% | 不适用 |

**「关掉之后的行为」是最容易写错的一格。** 用户把后台异步关了，压缩不能跟着失效——必须**退回同步**。否则用户关掉它之后，长会话直接撞墙，而且撞墙的原因跟他的操作看着毫无关系。

**默认打开是对的**：同步阻塞意味着用户在最坏的时刻（桌子最满、上下文最贵）等得最久。默认异步反而是更安全的默认值。

### 提醒的设计：知会，不询问

用户侧给提醒，但要明确一点——**提醒是知会，不是询问**。用户不需要点确认，压缩照常进行。

Claude Code 在这件事上留过一句话，值得直接抄态度：自动压缩时会往摘要末尾追加

> Continue the conversation from where it left off **without asking the user any further questions**.

这是因为有用户报过 plan 被压缩后模型反复确认「我们刚才在做什么」的 issue（Claude Code #24686 / #13955 / #26532）。

（要「能撤销」是另一个功能——Claude Code 用 `/rewind` 处理。别把「确认」和「撤销」混在一起。）

## 附属二：手动压缩

**走第 3 层完全相同的流水线**，只是入口不同。三条要注意：

**一、优先用抽屉里的素材。** 有新鲜的素材就几秒搞定，没有就现场算（等一分半）。这也是后台异步顺带带来的好处。

**二、自定义指令必须显式接进摘要 prompt。**

Claude Code 有个实测：用户把压缩指令写进 `CLAUDE.md`，**354 次裸 `/compact` 里 0 次生效**（全部回落到内置模板）；改成内联 `/compact <内容>` 之后 7/7 生效。

所以手动压缩如果要支持「用户指定这次压什么」，得**真的把它拼进摘要 prompt**，别指望它从某个配置里自动被读到。

**三、给人一个「不用压缩」的选项。**

Claude Code 官方给用户的建议是「把 `/compact` 放在任务之间的空隙里」，而且明确说 `/clear`（零成本）和回退到已缓存前缀比压缩更省——它们只是放弃了连续性。

**任务换挡的时候手动压，是最省的**：那时缓存是热的（Claude Code 官方说压缩请求会 fork 主会话复用缓存前缀；缓存冷的时候压缩要全额重算）。

## 落到 V4 的现状

| 层 | 现状 |
|---|---|
| 第 0 层 | `cm:ref` 大文件归档是雏形，但**读回未接线（缺口 G2）** |
| 第 1 层 | 已有：`compactAiMessageForMemory`（约 2400 字符阈值） |
| 第 2 层 | **缺**——这是要新建的 |
| 第 3 层 | 已有：`trySummarizeOldestRoundsIfNeeded`（>3 轮合并最早 2 轮）——**但是同步阻塞的** |
| 附属一 后台异步 | **缺**——而且第 3 层现在是同步的，改造时要把第 3 层**拆成后台半 + 前台半** |
| 附属二 手动压缩 | **缺** |

**建议的上线顺序**（每一步都能单独验证，不用一次全上）：

1. **先补 G2**——把 `cm:ref` 的读回链路接通。**第 0 层不闭合，往上叠第 2 层只会让「取不回来的东西」变多。**
2. **补第 0 层**——工具结果入历史前加一道独立预算（独立于压缩，别混进去）。
3. **补第 2 层**——借 OpenCode 的两个数字，加「不够门槛不提交」。
4. **补第 3 层的熔断和 no-op 检测**——现在的 `trySummarizeOldestRoundsIfNeeded` 有没有熔断、有没有「压完 token 没降」的检查？这两个不补，长会话会空转烧钱。
5. **把第 3 层拆成「后台半 + 前台半」**——这一步是异步化的地基，但**先不加异步调度**。拆完之后同步跑，只是代码结构上分开了。这样做的好处是：能先量出「素材」这条路的质量和滞后到底多大，再决定要不要真异步。
6. **加后台调度 + 可观测 + 熔断**——后台触发点、成功标记、`computed_through`、设置项。
7. **最后才是手动压缩**——成本最低、收益最直接，随时能做。

**为什么第 5 步要和第 6 步分开**：一次全上完，出问题你分不清是「拆得不对」还是「调度不对」。分开之后，第 5 步的输出可以直接和现在的同步版本对比（同样的输入、同样的阈值，看素材的质量差异）。

## 四条最容易踩的坑

**一、绝对阈值会随模型漂。**

OpenCode #45168：某模型声明 context 256,000 / output 64,000，按公式算出阈值 224,000，但真实输入上限只有 196,608——**阈值永远够不到，自动压缩永不触发**，每次全额重发 196K。
Hermes #14690：64K 小模型上阈值算出来等于整个窗口，**同样永不触发**。

所以第 3 层的阈值**必须是比例为主 + 一个绝对上限兜底**，不能只用绝对值。

**二、小窗口必须抬高下限。**

Hermes 的设计：窗口小于 512,000 时阈值从 0.50 强行抬到 0.75。理由是有些东西**压不掉**——system prompt + 几十个工具的 schema，加起来 20-30K token。在 200K 窗口上按 0.50 触发，压完回收的空间还不够抵消这个固定开销，结果**每压一两次又满了，再压**。

**这条对你也成立**：先量一下你那个 `@SystemMessage` 加上工具定义的固定开销有多大。如果在 32K 窗口上占比超过 50%，任何按比例算的阈值都会失效。

**三、摘要模型不能随便选小的。**

Hermes 官方把「摘要模型比主模型小」称为压缩质量下降最常见的原因——摘要调用会吃 context-length 错误、返回 None，**中间那段被无摘要丢弃**。

这直接推翻「摘要这种活随便找个小模型干」这个很自然的省钱想法。

**四、异步之后，压缩变得看不见了。**

同步的时候，界面卡一下就知道「在压缩了」。**异步之后压缩悄悄发生在后台——出错了用户完全不知道，只是突然发现模型开始忘事。**

Claude Code 那批「压缩后忘事」的 issue，有一大半是这个形态：界面上什么都没发生，但摘要其实失败了或者返回了空内容。

所以异步化**必须同时做三件事**，缺一不可：

| 给谁 | 做什么 | 为什么 |
|---|---|---|
| 用户 | 提醒（知会，不询问） | 让他知道正在整理，不要以为卡死了 |
| 用户 | 设置开关（默认开，关掉 = 退回同步） | 给他控制权 |
| **前台代码** | **检查素材的两个标记，不合格就现场算** | **这一条不能靠提醒替代** |

前两条解决「用户不知道」，第三条解决「代码不知道」。**只有第三条是硬性的。**
