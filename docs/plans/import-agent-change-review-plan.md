## 1. 目标与范围

让普通源码改动也经过 harness 的明确门禁：机器证明“候选真实、记录完整、边界未突破”，用户决定“这些改动是否接受”。

- 导入项目所有 Agent 编辑结果必须确认，包括 README、普通配置和普通业务文件；不按模型判断的风险等级跳过。
- 明确批准前，当前应用工作区保持原样。不隐式安装、启动、部署或发布候选。
- 人工批准不能覆盖机器校验失败；不新增模型审批、不自动推断业务合理性。
- 本期整批批准或整批拒绝，不做部分文件勾选合入、候选在线修改、自动批准或管理员代批。
- 保留保护路径、来源/视图/授权/候选四份依据、真实字节核验、秘密恢复、Shell 偷改拒绝、构建产物分离、资源硬限额与恢复保护。

这里的“合入”指替换平台内该应用的源码工作区，不是把应用部署到生产环境。

## 2. 已核实的实现约束

- `ImportAgentEditExecution.execute()` 在 `verification.verify()` 后立即 `publication.publish()`，没有最终人工批准。
- VERIFIED 是候选子表的 phase；父编辑此时仍是 SEALING。
- 主表 authorized_json 在 beginPublication 时才写入，不能直接作为等待确认阶段的数据来源。
- manifest changes 是 path、before、after；before/after 为 SHA-256、字节数与模式指纹，不是文本 diff。
- execute 的 finally 会清理资源，流还有总时限；不能用提前返回或长连接阻塞来实现等待。
- 父账本冻结了执行者身份与 expires_at。发布要求当前执行者；不能为了等待或重启续跑随意改写。
- discardable 当前要求 candidate_hash 为空。必须区分“等待候选”与“已进入发布”，不能混用清理判断。
- AgentRunPersistence 在流正常结束时按默认 FAILED 收口。等待事件、agent_run 状态和前端结束处理必须同步调整。

## 3. 推荐流程

```text
隔离编辑
  → Worker 与编辑容器真实停止
  → SEALING：Java 独立核验，候选 phase=VERIFIED
  → 生成并冻结审阅清单
  → WAITING_REVIEW：结束本轮执行流，保留候选与资源登记
      ├─ 用户批准：重新核验，原子登记批准与发布意图，进入 COMMITTING
      │             → 既有目录合入、提交和清理 → SUCCEEDED
      ├─ 用户拒绝：CANCELLING → 确认清理 → CANCELLED
      ├─ 到期：撤销资格 → 既有恢复/取消收口
      └─ 后端重启：撤销旧资格 → 既有恢复/取消收口
```

推荐本期重启后取消，而不是恢复等待。原执行者与有效期已经冻结，复用既有安全收口更小、更明确；这不是失败后的降级，不提供“续跑不成就自动取消”的双路径。

用户可刷新页面恢复等待，但不能跨后端重启继续批准旧候选。重启后提示“服务重启，本次待确认修改已取消，请重新发起修改”；清理未确认时必须显示恢复未完成，不能提前显示已取消。

## 4. 状态与持久数据

### 4.1 父编辑状态

新增 WAITING_REVIEW；候选子表继续保留 VERIFIED，不新增第二套候选状态。

- SEALING → WAITING_REVIEW：候选独立核验成功，清单已完整持久化，Worker/容器停止证明齐全。
- WAITING_REVIEW → COMMITTING：必须存在当前所有者对完全相同审阅版本的有效批准。
- WAITING_REVIEW → CANCELLING / RECOVERY_REQUIRED：拒绝、过期、版本失效或重启撤销。
- 封堵 SEALING → COMMITTING 的自动合入路径；不能保留给旧调用者绕过批准。
- 所有父状态更新仍要求 revision=old+1；终态不可回退，取消意图不可撤销。

等待时 publish_phase=NONE。父 candidate_hash、authorized_json 仍由开始发布写入，避免破坏既有发布冻结语义；等待绑定信息存到审阅登记，不要求把父 candidate_hash 提前填入。

### 4.2 审阅登记

新增 `biz.project_import_agent_edit_review`，每个 edit_id 唯一一份，不建设通用审批引擎。

建议字段：

- edit_id（主键及父编辑外键）、waiting_revision。
- candidate_hash、candidate_manifest_hash、authorized_state_hash、review_hash。
- changes_json：由 Java 核验后的清单生成，包含路径、改动类型和前后指纹。
- decision：PENDING / APPROVED / REJECTED / EXPIRED / REVOKED。
- decision_request_id、decided_by、decided_at、created_at。

review_hash 使用固定版本和确定性序列化，覆盖编辑身份、源版本、配置版本、context_epoch、等待 revision、候选/manifest/授权摘要及完整 changes。不能取模型给出的总结作为批准对象。

清单与所有身份/摘要插入后不可修改。决定只允许 PENDING 向一次最终决定推进；重复相同请求只读回结果，不再次启动发布。数据库守卫独立验证归属、等待 revision、候选 VERIFIED 证据及决策绑定。

清单与父状态推进必须同事务提交。崩溃不能留下“等待状态但没有清单”；落库失败保持失败/恢复路径，不发送等待事件。

## 5. 审阅内容与秘密边界

### 5.1 必交字段

逐文件展示相对路径、新增/修改/删除、前后 SHA-256/字节数/权限模式。改动类型由实际前后存在性确定，不相信模型标签。

- 清单来源为 Java 已核验的 manifest changes；通过类型化 VO 白名单投影。
- authorized 路径不等于实际 changed 路径；创建后再删除等空改动不冒充真实变更。
- 不展示私有绝对路径、秘密映射、原始 manifest、工具输出或执行产物内容。
- 构建产物单独标记为执行产物，不混进源码批准清单。

### 5.2 让普通改动可理解

仅显示哈希不足以判断普通修改是否合理。对于可安全展示的文本，增加按文件加载的去秘密前后对比；这仍属于结果审阅，不引入机器业务判断。

- 复用现有去秘密基线和秘密恢复规则，从独立原内容重建安全 before，读取已封存视图的安全 after；两侧先对相应冻结摘要，再生成对比。
- after 必须来自 Java 已验证的授权视图，不能将含恢复秘密的发布候选原文直接传前端。
- 原秘密绑定整行按既有规则保持不变；标记在 UI 中显示为“已隐藏的配置值”，不带出映射。
- 实施前用反例证明 before/after 通道均无原秘密及已知编码泄漏；安全展示无法确认时不得输出原文，也不得生成假 diff。
- 二进制、非可解析文本明确显示“无法显示文本差异”，仍提供完整指纹。大文件对比有界、分页，明确显示未加载范围，不能把截断内容称为完整差异。
- 所有差异按纯文本渲染，禁止 v-html、脚本执行或 Markdown HTML 注入。

此显示能力不得改变候选、扩大授权或允许重新上传批准内容。服务端始终批准冻结的完整候选，不批准浏览器传回的文件正文。

## 6. 批准、拒绝与发布门禁

### 6.1 拟定接口

沿用项目 controller/service 分层与 BaseResponse，不直接暴露 Entity。

- `GET /project/import/{appId}/agent-edits/current`：所有者找回当前待确认/恢复/发布任务。
- `GET /project/import/{appId}/agent-edits/{editId}/review`：获取当前状态、审阅绑定和清单。
- `GET /project/import/{appId}/agent-edits/{editId}/review/file`：校验相对路径属于清单后，返回有界安全文本对比。
- `POST /project/import/{appId}/agent-edits/{editId}/decision`：批准或拒绝。

决定 DTO：requestId、revision、candidateHash、candidateManifestHash、reviewHash、decision。ID 和 revision 对前端使用 string；所有者取登录态，不相信客户端 ownerId。授权摘要由服务端核对。

所有写接口沿用导入请求的登录、归属及 CSRF 保护。查询、分页与差异读取同样核对所有者和当前资格。

### 6.2 批准顺序

1. 取得应用许可与工作区协调锁，锁顺序与既有生成/删除一致。
2. 重读父编辑、审阅、候选 proof；核对 WAITING_REVIEW、revision、完整摘要、所有者、未取消、未过期、当前执行者。
3. 重新核对实际原工作区完整版本、配置版本与 context_epoch；重读候选库存/manifest并核验真实字节。等待期间任何变化都拒绝，不用旧 proof 替代当前内容。
4. 服务端构造发布路径与意图。在同一事务中消费 PENDING 决定、CAS 进入 COMMITTING、登记发布 journal 及必要产物意图；任何失败全部回滚，不留下可被另一条请求复用的悬空批准。
5. 后台执行既有合入与资源清理，不再次调用模型；每次目录移动及数据库提交前仍核对资格。接口受理不代表发布成功，前端查询最终状态。

`ImportAgentPublication.publish()` 的两个重载和 ledger.beginPublication 都必须走同一人工批准门禁。不能只保护新增控制器而保留内部自动发布捷径。

审批事务与既有 outputs.plan 的事务/资格条件实施时一并对齐：不能提前改变发布 phase 使现有产物守卫失效，也不能放宽成“只要候选 VERIFIED 就能发布”。

批准和拒绝共用 requestId 幂等：同 requestId、同绑定、同决定返回既有结果；换决定或换摘要返回冲突。不同 requestId 的并发决定只能有一个 CAS 成功。

### 6.3 拒绝与失败

拒绝是整批丢弃，不是把候选回写原工作区。事务登记 REJECTED 并进入 CANCELLING，随后按已有停止证明、候选/卷/视图释放顺序清理。

- 不调用发布；原工作区完整哈希不变。
- 只释放明确绑定本编辑的资源，留决定与摘要审计，不留可执行半成品。
- 清理失败保留资源、占用和失败依据，显示“清理未完成”，不能假报 CANCELLED。
- 发布已进入 COMMITTING 后不允许新拒绝请求直接中断目录移动；按现有未决发布恢复规则处理。

## 7. 流、任务与等待期资源

- 候选和清单持久化成功后发送 `import.edit.review.required`：仅携带编辑身份、等待 revision、候选/清单摘要和必要计数；展示过滤器必须明确允许安全字段。
- 待确认结果不是 RUN_COMPLETED/succeeded。流可正常结束，但 agent_run 登记 WAITING_REVIEW，不触发成功提示、自动运行、成功制品刷新或默认 FAILED。
- SSE 与 WebSocket 共用同一事件和查询接口。事件丢失或页面刷新由数据库找回，不以事件抵达作为批准依据。
- 等待前确认 Worker 和编辑容器已停止；归还 Worker 池槽位，释放本轮内存锁/订阅线程。保留已登记候选、私有映射与容量卷，并继续计入硬配额。
- execute 的 finally 明确区分“已移交等待审阅”与“未完成需清理”。只在等待状态与清单已落库后保留资源，异常/取消不得伪装成等待。
- 等待期不长期持有 AppRunCoordinator 信号量。改用数据库未关闭编辑登记阻止同应用新编辑、保存、运行/安装、变更配置和删除；只读浏览原工作区及审阅允许。
- 新准入检查必须覆盖实际写入口，并放在既有应用锁内，不能只靠前端禁用按钮。同应用排队请求拿锁后重读；跨应用不受影响。
- 等待期间网络断连不等同于拒绝；进入等待前的取消仍按原规则处理。迁移前已明确取消的任务不能被移交等待。
- 保留原 expires_at，不暗中延长。定时扫描到期等待项，CAS 撤销并安全清理；任务资源失败仍保留。后台停止时不自动批准。
- 批准后同一 run 最终更新为 SUCCEEDED/FAILED/取消收口结果。聊天、任务对账、统计及完成事件需识别等待状态，避免孤儿恢复误判或重复写一条“已成功”的 AI 消息。

## 11. 完成门禁

以下每项需当前实现版本的可运行检查与独立读回，不能沿用历史通过数字：

1. 合法修改普通 README、普通配置与业务代码；验证后进入等待，原工作区及哈希未变。
2. 新增/修改/删除清单与实际变更一致；空授权操作不生成虚假改动，执行产物不混入。
3. 用户批准后仅发布一次，最终实际文件符合候选；成功前清理读回，正确写入任务与决定。
4. 用户拒绝不发布，原内容不变，资源与占用确切释放；注入清理失败时保留资源并明确失败。
5. 无批准直接调用两种 publish 入口、beginPublication 或直接 SQL 提交全部拒绝。
6. 旧 revision、候选/manifest/review 摘要错配、伪造所有者、跨应用请求拒绝。
7. 候选真实字节、manifest、原源码、配置或 epoch 等待期变化均不能按旧批准发布。
8. 重复批准幂等；批准/拒绝并发、批准/过期并发、取消/移交等待竞态只产生一个合法结果。
9. 页面刷新与等待阶段断连可找回；执行阶段取消不能残留成待确认；等待时 Worker 池不占槽。
10. 后端重启识别待确认旧任务，按既定取消收口；停止/释放失败保留证据，旧按钮永远不能发布。
11. 等待过期正确回收；跨应用仍可执行，同应用受管写入/安装/运行/删除不会绕过占用。
12. 发布移动窗口中断保持现有恢复正确；已提交源码不因审阅恢复被回退。
